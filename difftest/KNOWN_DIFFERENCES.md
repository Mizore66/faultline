# Known differences between Go `fl` and frozen TS (`ce99a79`)

Every intentional divergence is listed here. Anything not listed is a bug.

The oracle is frozen TS at `ce99a79` (`v0.1.10-buildweek`), the `src/` CI has built since slice 1. Slices 1 and 2 named `faa98c0` (`v0.1.9-buildweek`) as the pin, but `14ad89d` and `ce99a79` changed `src/` after it (slice 3 spec, section 3.1); every entry below was measured against the `ce99a79` build.

## Locale-dependent key order (TS bug, not reproduced)

TS `canonicalJson` sorts object keys with `localeCompare`, which uses the machine's ICU default locale. Under `sv-SE`, Node sorts `å ä ö` after `z`; under `tr-TR`, it orders `I` before `i`. Go always uses the en-US (CLDR root) order that CI and `C.UTF-8` machines produce. Bundles written under an affected locale with affected keys already fail TS verification on en-US machines.

Go's collation (`internal/collation`) is generated from the ICU 78 root collation data (Unicode 17, CLDR 48) that official Node 22 builds ship from 22.22.1 on, and follows ICU's comparison, not a plain UCA key compare: `internal/collation/iter.go` ports ICU's `FCDUTF16CollationIterator` and `CollationIterator` (incremental FCD check, contraction and discontiguous-contraction matching with its look-ahead and backtracking, prefix contexts), so mark runs that ICU leaves un-normalized after contraction look-ahead collate as in ICU; ICU's contraction and prefix data (U+FDD0 rows excluded as genuca does); and `RuleBasedCollator::doCompare`'s identical-prefix skip and early exit at the first primary difference. The identical-prefix skip makes `localeCompare` non-transitive on some inputs, so `SortLocale` runs a port of V8's TimSort. Parity is checked against Node by `TestLiveCollationAllCodePoints` (every code point), `TestLiveCollationRules` (every contraction and prefix key with inserted, reordered and dropped marks and U+FDD0/U+FDD1 sequences), `TestLiveCollationMarkRuns` (contraction starters followed by supplementary and BMP mark runs, each string against its NFD and NFC forms, reorderings and shared prefixes) and `TestLiveSortLocale`.

**Minimum Node version.** Earlier Node 22 releases bundled ICU 74 (22.0), 75.1 (22.1) and 76/77 before ICU 78. Bundles written by those releases whose overlay paths or JSON keys contain characters assigned after their Unicode version (for example U+1FAE9, Unicode 16) may use an order Go rejects (`overlay records are not in canonical path order`, or a different canonical-JSON digest). Current Node 22 TS agrees with Go. A Node built against a system ICU (`--with-intl=system-icu`) can differ the same way.

## Directory listing order on Windows

Node's `readdirSync` returns byte-sorted names on Linux and macOS but filesystem order on Windows (NTFS: case-insensitive upcase order). Go returns byte-sorted names everywhere, so Go on Windows matches TS on Linux. This affects the order of error lines that enumerate files, and, because the file walkers stop at the first symlink, special file or oversized file they meet, which file such an error names when a bundle has two offending entries (for example `analysis.json` before `ROOT.sha256` on NTFS, the reverse in byte order).

## Git's default object format

Not an output difference, but an environment dependency of both implementations. The verifier creates its temporary repository with a plain `git init --bare` (`src/git-proof-bundle.ts:931`), which follows `GIT_DEFAULT_HASH` and `init.defaultObjectFormat`. A SHA-1 bundle therefore verifies only where git defaults to SHA-1, and a SHA-256 bundle only where it defaults to SHA-256; elsewhere both report `Git bundle extraction failed`. Go runs the same git commands and matches TS in both settings. The golden generator and replay pin `GIT_DEFAULT_HASH=sha1`, and the `git-sha256` base runs with `GIT_DEFAULT_HASH=sha256` (`difftest/testdata/base-env.json`).

## Git bundle bytes across git versions

Not an output difference between the implementations: both write `descendant.bundle` with `git bundle create`, so the bundle's bytes (pack compression and delta choices) and, through its digest, the manifest and `ROOT.sha256`, follow the installed git. Within one machine Go and TS produce the same bytes, which the writer replay and `TestWriterSameDirectory` compare. The committed writer goldens record the bytes of the git that generated them; `difftest-live` regenerates them on ubuntu-24.04 and fails on drift, so a runner whose git packs differently changes those goldens' bundle digests in both implementations alike.

## SHA-256 repositories cannot be published (TS behaviour reproduced)

`investigate git` on a repository with `extensions.objectFormat=sha256` fails in TS and in Go with `Refusing to publish an invalid Git proof bundle: portable Git source verification failed: Git bundle extraction failed: …`: the stage verifier's plain `git init --bare` creates a SHA-1 repository unless `GIT_DEFAULT_HASH=sha256` (see the previous section), and git cannot index the SHA-256 pack into it. This is a TS bug that Go keeps for parity; the writer case `investigate-sha256` and `TestInvestigateRefusalLeavesNoStage` record it, including that no staging directory is left behind.

## Docker diagnostics

Not an output difference between the implementations: both pass the `docker` CLI's and daemon's stderr through into the run records and errors, so their wording follows the installed Docker. The writer goldens use scripted fake Dockers (`difftest/testdata/fakedocker`), whose diagnostics are fixed text, and `TestLiveRealDocker` runs both sides against the same daemon and compares stderr unmasked; on another Docker version both implementations print that version's text.

`runtime project build`'s status follows the daemon's image store, in both implementations alike: with Docker's classic store a local build records no RepoDigest, so the build ends `PROJECT_IMAGE_BUILT_NEEDS_REGISTRY_DIGEST` (exit 1); the containerd store (Docker 29's default) records one, giving `PROJECT_IMAGE_PREPARED_LOCAL_DIGEST` (exit 0); podman records `localhost/<repository>@sha256:…`, which both refuse with `UNEXPECTED_REPOSITORY`. `TestLiveRealDockerProjectBuild` compares TS and Go on whichever store the daemon uses; CI forces the classic store.

Host tool versions are not compared outside the fake toolchain: `doctor` prints the installed `git --version`, `node --version` and `docker --version` lines, and the writer goldens use the fixed answers of `difftest/testdata/faketools`. The turn-snapshot quiescence wait (50 ms per attempt, up to 4 attempts) is wall time; only the number of attempts reaches the output.

## V8 limits

When a zod schema rejects a deeply nested value, TS builds the error text with `JSON.stringify(issues, replacer, 2)` (the `ZodError.message` getter). V8 does this recursively, and past its native stack limit it throws `RangeError: Maximum call stack size exceeded`, which the verifier's catch prints as a `failed safely` line. Go models V8's stack use (`internal/jsjson/stack.go`): each non-empty array or object pushes a frame, empty containers and primitives push none, and objects on V8's slow path (array-index keys, or 128 or more members, which JSON.parse builds in dictionary mode) cost more. The model is fitted per platform and per call site (demo, prevention, git, the git lifecycle ledger, and the demo witness artifact, whose messages are read from deeper JS frames). On Node 22.22.2 linux/amd64 (glibc) it reproduces every measured threshold at every site exactly: the demo verifier still prints the zod message for 2,233 nested arrays, 4,166 single-key objects, 2,232 index-keyed objects or 2,906 alternating arrays and objects, and one more level overflows. The witness site gives 2,232 / 4,164 / 2,231 / 2,905. darwin/arm64 and linux/arm64 are fitted to Node 22.22.2 too (the release CI pins), from the stack-live CI job's measurements at all five sites, and `TestLiveStackThresholdsMatchNode` bisects every site and shape against `node dist/cli.js verify` on linux/amd64, linux/arm64 and darwin/arm64 in CI. Values that mix shapes on the way down (alternating index-keyed and named objects; array, named and index-keyed objects in turn; and the like) can overflow one level earlier or later in TS than the model predicts, at every site and on every platform measured: the per-frame costs are fitted to the pure shapes, and the rounding adds up differently on mixed ones. Measured (last depth whose schema message prints, TS vs Go): linux/amd64 ledger 2,905 vs 2,906 and 2,639 vs 2,640; linux/arm64 prevention manifest 2,104 vs 2,103 and 2,549 vs 2,548, demo manifest 1,869 vs 1,868, prevention body 2,185 vs 2,184; darwin/arm64 demo 3,536 vs 3,535 and 3,162 vs 3,161, witness 2,547 vs 2,548, ledger 3,160 vs 3,161, git frozen record 4,102 vs 4,101 and 3,160 vs 3,159, prevention body 4,112 vs 4,111. At such a depth one side prints the schema message and the other `failed safely: Maximum call stack size exceeded`; both are INVALID. Dictionary mode follows V8's JSON.parse: an object literal with 128 or more named entries, duplicate keys included and index keys excluded, is on the slow path. Other builds are not fitted: musl builds (node:alpine) cost differently from glibc on the same architecture (linux/amd64 Node 22.22.2 musl: arrays 2,155, alternating 2,840, index-keyed 2,231; glibc 2,233, 2,906, 2,232; linux/arm64 differs by up to 78 levels), the stack costs drift between Node releases (darwin/arm64 prints 2,610 nested arrays on 22.22.2 and 2,747 on 22.23.2; linux/arm64 1,781 on 22.13.1 and 1,827 on 22.22.2), and Windows and other targets use the Linux model for their architecture. On those, TS can overflow tens to hundreds of levels earlier or later than Go predicts. `--stack-size` also moves V8's limit. `JSON.parse` is iterative on both sides and has no depth limit.

Go also reproduces V8's other size limits: strings longer than 0x1fffffe8 UTF-16 units (`RangeError: Invalid string length`, from `JSON.stringify`, every error message that embeds input, which Go builds with `jsexc.Concat` where TS uses a template literal, and the CLI's error join), Sets and Maps with more than 2^24 entries (`RangeError: Set maximum size exceeded` / `Map maximum size exceeded`, at the Go ports of the TS Sets and Maps, all of which are built before any comparison as in TS), and argument spreads (`errors.push(...list)`, `files.push(...collectFiles(...))`), which throw `Maximum call stack size exceeded` once the list passes V8's stack. The limits were bisected exactly through `node dist/cli.js verify` on Node 22.22.2: the demo walker passes 125,576 files one directory below the bundle root on linux/amd64 (31 fewer per further level), 110,189 on linux/arm64 and 110,181 on darwin/arm64 (32 fewer per level); git semantics errors 125,587 / 110,201 / 110,193; lifecycle-ledger errors 125,562 / 110,175 / 110,167. Node built on musl overflows about 20 elements earlier on linux/arm64, windows/arm64 uses the linux/arm64 values and other targets the linux/amd64 ones; on darwin/amd64 that is off by four (the TS walker passes 125,572 files, Go 125,576), and the rest have not been measured. Node 22's `rmSync(path, { recursive: true })` is the recursive JS `rimrafSync`, so removing the git verifier's temporary bare repository overflows V8's stack when it holds an entry more than 1,672 levels deep on linux/amd64 or 1,375 on linux/arm64 (Node 22.22.2, glibc and musl; a file and an empty directory count alike), for example from a deep global `init.templateDir` or a hook. Go's rimraf throws the same `Maximum call stack size exceeded` at that depth and leaves the tree behind as TS does; darwin cannot reach the depth (PATH_MAX). The walker's limits were fitted on bundles whose walk is short. Once the walk has run tens of thousands of iterations before the big spread (60,000 files in the root, or 20,000 directories), V8 has tiered `collectFiles` up and Node overflows 6 elements earlier at the same depth (110,175 instead of 110,181 on darwin/arm64, 110,183 instead of 110,189 on linux/arm64), so a directory holding 110,176 to 110,181 files at depth 1 on darwin/arm64 (110,184 to 110,189 on linux/arm64) makes TS fail safely with a stack overflow, where Go walks it; the model does not follow V8's tiering. `TestLiveSpreadLimitsMatchNode` checks the spread limits against Node on linux/amd64, linux/arm64 and darwin/arm64 in CI, and `TestLiveRimrafDepthMatchesNode` the rimraf depth on Linux (it skips on darwin, which cannot reach the depth). Some allocations make V8 abort the process, and Go aborts the same way. JSON.parse arrays of 2^27 or more elements print the V8 fatal-error header with the real length (`# Fatal JavaScript invalid size error 134217729 (see crbug.com/1201626)`) and die by SIGTRAP (exit 133). An object's index-keyed entries (duplicates included) go into a NumberDictionary when that is smaller than a FixedArray up to the largest index (V8's `ShouldConvertToSlowElements`: 9 × the dictionary capacity for the entry count, at most the largest index + 1), otherwise into that FixedArray: a FixedArray of 2^27 or more slots aborts the same way without the crbug note (`{"0":0, …5,592,406 entries…, "134217727":0}`), and a dictionary of 22,369,622 or more entries fails like a NameDictionary of 22,369,622 or more named entries (duplicates included): Node's `FATAL ERROR: invalid table size Allocation failed - JavaScript heap out of memory` report and SIGABRT (exit 134). `String.prototype.split` into 2^27 or more parts aborts like the FixedArray (a demo `hashes.txt` of 134,217,728 lines or more). Arrays V8 grows one push at a time (to 17, 43, ..., 75,209,227, 112,813,858 slots) cannot reach 112,813,859 elements, and Go throws the same catchable `RangeError: Invalid array length` there: from the demo verifier's `.filter(Boolean)` over `hashes.txt` lines (inside its try, so `failed safely`), and from its `errors` list, whose catch block then fails to push as well, so the error reaches the CLI (`FaultLine error: Invalid array length`, nothing on stdout). Node's heap limit is not modelled: with the default heap, Node dies of heap exhaustion (exit 134) on a demo `hashes.txt` of tens of millions of invalid lines that `fl` reports, and under a memory limit a text file that never ends (a link to `/dev/zero`) gets either killed. Go builds the object before it aborts where V8 aborts while sizing it, so under a memory limit that Node's peak fits in (about 2 GB for 22,369,622 named keys) Go can be killed by the OOM killer (exit 137, no output) instead. Node's GC trace, native stack trace and `#FailureMessage Object` address are not reproduced. A utf8 read of a file of 0x1fffffe8 bytes or more fails with `Cannot create a string longer than 0x1fffffe8 characters` in both. Both read to the end of the file without calling fstat (Node's `ReadFileUtf8`), so the size a filesystem reports does not matter; but Node keeps every byte before checking and Go only counts the bytes past the limit, so under a memory limit smaller than the file TS is killed by the OOM killer (exit 137, no stdout) where Go prints the error.

Writers hit the same limit at the CLI: `fl witness propose --input` with a deeply nested value in the proposal builds the zod message when `formatCliFailure` reads it, at its own stack site (`jsjson.SiteCLI`, fitted per platform like the verifier sites and checked by `TestLiveStackThresholdsMatchNode`'s `cli` site). Up to that depth both print the same message. Past it, TS's `ZodError.message` getter throws an uncaught `RangeError` and Node prints its own crash report (the zod source line with a caret, `RangeError: Maximum call stack size exceeded`, a stack through the install's `node_modules` and `dist` `file://` paths, and `Node.js v22…`), exit 1; Go prints `FaultLine error: Maximum call stack size exceeded` and the `Next: pnpm fl help` hint, exit 1. Both write nothing. Node's report depends on the install path and Node version, so it is not reproduced.

`fl init` reaches the same limit at two more sites: the zod message for a deeply nested value in `.faultline/config.json` (read by `fl init` and printed by `formatCliFailure`, `src/config.ts:62`), and in `.faultline-secret-allowlist.json` (read by `fl init --yes`'s pre-warm snapshot, whose catch reports the message as `snapshotPrewarm.reason`, `src/turn-snapshot.ts:1171`). TS's overflow depth there is not deterministic: init reads these files after awaiting child processes, and on Node 22.22.2 the same value prints the zod message in one run and overflows in the next. Bisected over three runs, TS's last printing depth lies 0 to 63 levels below Go's on linux/arm64 and 14 to 241 below on darwin/arm64, and moves from run to run; linux/amd64 is measured by CI's difftest-live job, whose "Measured stack depths" step annotates the band. Go's depth is fixed (the config message is read at `jsjson.SiteCLI`, the allowlist one at the default site), so inside that band TS may overflow where Go prints the message. Past it, TS prints Node's uncaught `RangeError` report for the config (as at the `cli` site above) and `Maximum call stack size exceeded` as the allowlist's `snapshotPrewarm.reason`; Go prints `FaultLine error: Maximum call stack size exceeded` and the same reason. `TestLiveStackThresholdsMatchNode` marks these two sites unstable and requires Go to stay within 512 levels of TS's bisected depth, which catches a missing or grossly wrong limit, not the band.

## Stdout write errors

Go builds stdout the way Node's `createWritableStdioStream` does, from a port of libuv's `uv_guess_handle`. A regular file or character device is a `SyncWriteStream`: one `write(2)` per chunk, a short count ignored (a full disk or `RLIMIT_FSIZE` reached in the middle of a chunk truncates the output silently), and a failing call reported as `Error: <CODE>: <description>, write` (`/dev/full` gives `Error: ENOSPC: no space left on device, write`). A pipe, stream socket or terminal is a libuv stream: everything is written, waiting while the descriptor would block (for example after another process set `O_NONBLOCK` on a shared pipe), and a failure is `Error: write <CODE>`. UDP sockets and handles libuv cannot classify (a datagram Unix socket, a directory) get Node's dummy writer, which discards the output. As in Node, stdout is classified on first use (the first write, after the checks), so a terminal that hangs up during verification gets the file form, and a terminal, pipe or FIFO that fd 1 has open read-only is a stream libuv cannot write to, which fails with `Error: write EPIPE` without a write. Both runtimes ignore SIGPIPE, so a pipe whose reader has gone is `Error: write EPIPE`, and any stdout write error exits 1. On Windows, Node writes pipes synchronously, so a pipe error has the file form, `ERROR_BROKEN_PIPE` and `ERROR_NO_DATA` are `EPIPE`, and a handle not opened for writing is `EBADF` (`fs__write` turns `ERROR_ACCESS_DENIED` into `ERROR_INVALID_FLAGS`), as in libuv. On a stream, `ENOBUFS` waits like `EAGAIN`, and on macOS `EPROTOTYPE` is `ECONNRESET`, as in `uv__try_write`. Error codes come from libuv's full `uv_err_name` table; an errno it cannot name is `Unknown system error -N` in both forms, as in every error Node throws from C++ (the fs calls and `uv_cwd` included). Node reports the error as an unhandled `'error'` event, a stack trace around the error line; Go prints the error line only. `TestLiveStdoutMatchesNode` compares these cases with Node on Linux. The CLI's own error output goes through `process.stderr`, which Node creates while its modules load, so fd 2 is classified at startup and gets the dummy writer for UDP and unclassified sockets too (`FaultLine error:` lines reach a TCP or stream socket but not a datagram or `SOCK_SEQPACKET` one); V8's fatal reports and the stdout error line are printed with C stdio and reach fd 2 whatever it is, in both (`TestLiveStderrMatchesNode`, Linux and macOS). On a Windows console Node decodes the output to UTF-16, writes an LF not preceded by CR as CR LF, and calls `WriteConsoleW` (libuv's `uv__tty_write_bufs`), and Go does the same; its errors are libuv's stream errors (`Error: write EPERM` for a handle not opened for writing). This was checked against libuv's source, not on a Windows console. One oracle pathology is not reproduced: when stdout or stderr is a pseudo-terminal whose master has already closed, Node blocks forever in `uv_tty_init` reopening the terminal (for stderr on every command, even a VALID verify that writes nothing there); Go reports `Error: write EIO` and exits 1 for stdout, and runs normally for stderr.

## Signals and resource limits

Node resets signals 1 to 31 to their default action at startup, ignoring only SIGPIPE and SIGXFSZ, clears the signal mask, and raises its soft `RLIMIT_NOFILE` to the hard limit; libuv resets every signal and the mask in the processes it starts, which inherit the raised limit. Go emulates this from the first package initialized (`internal/boot`). On Linux the signals whose default action ends the process (HUP, INT, QUIT, ABRT, USR2, ALRM, TERM, STKFLT, XCPU, VTALRM, IO, PWR, SYS and the real-time signals from 35) are set to SIG_DFL in the kernel; externally sent SEGV, BUS, FPE, ILL and TRAP are caught and end `fl` by their default action (the Go runtime keeps its handler so that faults in Go code still panic); inherited SIG_IGN on TSTP, TTIN, TTOU and CONT is reset; and then an inherited signal mask is cleared by re-executing `/proc/self/exe` once with an empty mask, before the standard descriptors are marked close-on-exec, so the output reaches the same descriptors. Node clears the mask before it resets any disposition, so a signal left pending under the inherited mask meets the disposition the parent left: the default action, or nothing if it was ignored. Go does the same for the stop signals, whose inherited SIG_IGN is reset only after the mask is cleared, and for a pending SIGPIPE or SIGXFSZ the parent left at SIG_DFL, which ends `fl` before the runtime's signal thread can catch it. The Go runtime replaces the other inherited dispositions with its own handlers before any Go code runs and keeps the originals out of reach, so on Linux a C constructor (built when cgo is enabled, the default wherever a C compiler is installed) records which signals the parent ignored, and the image that clears the mask receives that record in `FAULTLINE_BOOT_IGNORED`, which it deletes at once. With it, a pending signal the parent ignored (SIGPIPE, SIGXFSZ, SIGUSR2, a real-time signal) is discarded as Node discards it, and a real-time signal inherited as SIG_IGN stays ignored in `fl` and in git, as in Node, whose libuv resets only signals 1 to 31 in children. A build without cgo cannot know: there such a pending signal ends `fl` (exit 140 for SIGUSR2, 141 or 153 for PIPE or XFSZ in a shell), and the real-time signal is SIG_DFL in git. Deaths go through `rt_sigaction`, `rt_sigprocmask` and `tgkill` on the dying thread, with core dumps where the kernel makes them. The soft `RLIMIT_NOFILE` is raised as Node raises it and git inherits it: to the hard limit, or, when the hard limit is `RLIM_INFINITY` (2^63 − 1 on macOS, where it is the default), to the highest value below 2^20 that `setrlimit` accepts (1,048,575 on macOS 26). Node starts that bisection at the inherited soft limit (so git gets 1,048,576, or no limit, when that is already 2^20 or more), which the Go runtime has replaced by the time `fl` runs; with an infinite hard limit `fl` therefore asks `/bin/sh` for it, which Go starts with the inherited limit, just before the first git, and bisects from there. `TestLiveNofileMatchesNode` compares git's limits with Node on Linux and macOS. `TestLiveSignalsMatchNode` compares the death, the output, and git's signal mask, ignored set and descriptor limit with Node on Linux, including a blocked mask, a signal pending under it (also raised before exec under SIG_DFL or SIG_IGN), and a low soft limit.

On macOS the same signals are caught through os/signal, since the syscall package exports no `sigaction` or `sigprocmask` there. For SIGHUP, SIGINT and SIGTERM, `fl` stops catching the signal and sends it to itself, and the Go runtime dies of it (SIG_DFL, unblock, raise); when the parent left SIGHUP or SIGINT ignored, or for any other signal, `fl` dies by re-executing `/bin/sh -c 'kill -N $$'`, after setting every other signal to SIG_IGN so that one arriving while the shell starts cannot replace the first (Node dies of the first). Go learns of a signal on a goroutine, a few milliseconds after Node would have died. `fl` therefore writes nothing and does not exit once a signal has reached it, and when a child dies of a signal `fl` did not send (Ctrl-C, a terminal hang-up or `killpg` reach `fl` and git together) it waits for its own copy until 2 s after git's death before it writes anything or exits (once per run, not per write; a child that died of a fault such as SIGSEGV or SIGABRT crashed by itself, so there is no wait), which delays the report but does not change it; `TestLiveGroupSignalMatchesNode` checks both on Linux and macOS. A signal sent to `fl` alone at the very end of a run can still let the report out first. A mask or SIG_IGN on the stop signals inherited from the parent stays in effect on macOS, and a `/bin/sh` that ignores SIGQUIT (bash) exits 131 instead. macOS delivers SIGBUS, SIGILL and SIGSEGV sent with `kill` with a fault code rather than the code of a user-sent signal, so the Go runtime takes them for a crash in `fl` and exits 2 with a goroutine dump where Node dies by the signal (SIGEMT, SIGFPE and SIGTRAP die correctly). When the parent left SIGBUS or SIGSEGV ignored, the runtime forwards such a signal to that SIG_IGN instead: `fl` carries on and can print `VALID` and exit 0, where Node, which resets them to SIG_DFL, dies by the signal. Linux is not affected. Rarely (seen about 1 in 40 times on a heavily loaded Mac in round 6, before group signals stopped going through the shell), the `/bin/sh` that `fl` replaces itself with crashes at start-up with SIGILL, so `fl` dies by SIGILL instead of the signal it received; this can still happen for the signals that go through the shell. Output is empty either way.

Remaining differences on every Unix system: a signal that arrives before the Go runtime has initialized any package (under a millisecond on an idle machine, over 10 ms on a heavily loaded one, and again while the image that clears an inherited mask on Linux starts) is handled by the runtime (ALRM, USR2 and the like are dropped, QUIT and ABRT dump goroutines); SIGPROF is consumed by the Go runtime, so it doesn't stop `fl`; SIGUSR1 starts Node's inspector (a "Debugger listening" line on stderr) and is ignored by Go. On musl, Node leaves signal 33 (musl's SIGCANCEL, installed only when a thread is cancelled) at its inherited disposition, so it dies of a `kill -33` and passes an inherited SIG_IGN on to git; glibc installs its own handler there (SIGSETXID), as the Go runtime does, and `fl` follows glibc, which a static binary cannot tell from musl. If the re-execution fails (no `/proc` mounted, as in a bare chroot or some sandboxes), `fl` continues with the inherited mask, and git inherits it too. On Windows, console control events follow the Go runtime, and on a console `fl` turns on `ENABLE_VIRTUAL_TERMINAL_PROCESSING` before its first write, as libuv does for Node, so escape sequences in the output are interpreted by the console; on a console that refuses that mode, libuv strips and applies the sequences itself, which `fl` does not reproduce (it writes them as they are). When closing a file it has read fails (an `EIO` from a FUSE or NFS flush, say), Node aborts on a CHECK for a text read and throws `EIO: i/o error, close` for a binary one; `fl` does the same, but prints the assertion header in the form a Linux build of Node 22.22.2 uses (macOS builds name the function differently) and none of the native or JavaScript stack trace that follows it.

Node keeps a few dozen file descriptors open for its event loop, thread pool, V8 platform threads and module loading. With a hard `RLIMIT_NOFILE` of about 30 or less, TS fails where Go still verifies (from 15; below that Go prints `spawnSync git EMFILE`). Measured with Node 22.22.2 on Debian 12 linux/arm64 for `git-two-states`, when the parent passes only descriptors 0 to 2: 31 verifies; 19 to 30 print `spawnSync git EMFILE`; 17 and 18 fail to open one of FaultLine's own `dist/*.js` files with `EMFILE`; 13 to 16 die by SIGSEGV with no output (exit 139); lower limits abort in `uv_loop_init` (exit 134). Other machines measured one lower (30 the first that verifies), and each further descriptor the parent leaves open raises the upper thresholds by one. The numbers change between Node versions, so they are not modelled.

## Starting git

`spawnSync` is ported from libuv and the C library Node's official builds use. On Linux the executable lookup is glibc's `execvp` (a candidate that fails with `ENOEXEC`, such as a script without a `#!` line, is run by `/bin/sh`; `ESTALE`, `ENODEV` and `ETIMEDOUT` move on to the next PATH entry; a PATH entry of 4,096 bytes or more is skipped and the bare name is tried in the working directory next; the default search path is `/bin:/usr/bin`); on macOS it is libuv's own search over `posix_spawn`. Child sockets get libuv's 64 KiB buffers, descriptors 0 to 15 and the run above them are close-on-exec from startup (`uv_disable_stdio_inheritance`), environment names that are array indices (and, on Linux, the empty name) are dropped as `{...process.env}` drops them, and an errno libuv has no name for prints as `Unknown system error -N`. On Windows git is created with `CREATE_NO_WINDOW`, in a kill-on-close job object, with 64 KiB pipes, without the hidden `=X:` variables, and with an 8.3 working directory when the cwd is 259 UTF-16 units or longer (libuv counts the terminating NUL against `MAX_PATH`, and searches for git from the short form); environment names that differ only in case are reduced to the first in sorted order, as `normalizeSpawnArguments` does on Windows. Remaining differences: when every PATH entry is skipped for length, glibc reports whatever errno was left over in the child (`EINVAL` or `ENOSYS` depending on the host), and Go reports `ENOENT`; Node built on musl (Alpine) has musl's `execvp`, which does not run `ENOEXEC` files through `/bin/sh`, searches `/usr/local/bin:/bin:/usr/bin` by default, skips a PATH entry of 4,096 bytes or more without trying the bare name in the working directory (so a `git` there runs under Go and not under TS), and ends the search on `ESTALE`, `ENODEV` or `ETIMEDOUT` where glibc moves on; a static binary cannot tell which C library the host's Node uses, so Go follows glibc; on macOS, Go starts git with fork and exec rather than `posix_spawn`, so a malformed Mach-O fails with `exit null` instead of `Unknown system error -85` (EBADEXEC), and libuv aborts Node outright when every PATH entry is too long; on Windows, Go sorts and deduplicates the names as `normalizeSpawnArguments` does and looks each kept name up again with `GetEnvironmentVariableW`, as Node's `process.env` does (so `Path=A` before `PATH=B` gives git `PATH=A`, and a lone surrogate in a value becomes three U+FFFD), but uppercases names with Go's simple case mapping where Node's `toUpperCase` maps a few letters to several (ß to SS); libuv lets git inherit every inheritable handle of the Node process, and Go only the three standard ones.

## Working directory errors and the C library

`process.cwd()` is libuv's `uv_cwd` over the C library's `getcwd`, and its error codes come from that library. Go ports glibc's `getcwd` on Linux (the `getcwd` syscall, then `__getcwd_generic`'s walk up through `..` when the kernel cannot return the path: longer than a page, or outside the process root after `chroot(2)`) and Apple Libc's on macOS (the `F_GETPATH` fast path checked against `.`, then the same kind of walk, keeping the first `fstatat` error), with `uv_cwd`'s retry that turns a path exactly one byte too long into `ENOBUFS`. `TestLiveCwdErrorsMatchNode` compares `verify` from deleted, recreated, over-long (short and long segments around 4,096 bytes), unreadable and chrooted working directories with Node on Linux. musl (Alpine) has no fallback walk: a cwd longer than a page gives `ENAMETOOLONG` and a cwd outside the root gives `ENOENT` there, where Go, like glibc Node, gives `ENOBUFS`/`ERANGE` and the real path. The macOS port has not been run here (the reviewers' macOS cases were checked against Apple's source). Other Unix systems use Go's `getcwd`.

## Directory listings on Linux

Node's `readdirSync` is libuv's `scandir`, which reads entries through the C library's `readdir`. glibc 2.28 to 2.36 (Debian 11 and 12, RHEL 8 and 9, Ubuntu 22.04) skips entries whose inode number is 0, which some FUSE filesystems and old XFS report for live files; glibc 2.37 and later and musl list them. One static binary cannot follow both, so Go follows glibc 2.36, the C library most LTS systems run Node on, in the bundle walkers, rimraf and the `getcwd` walk: on glibc 2.37+ or musl hosts with such a filesystem, Node sees files Go does not. Entries whose type libuv cannot name (`DT_UNKNOWN` from XFS without `ftype`, some NFS and FUSE, or any `d_type` other than FIFO, CHR, DIR, BLK, REG, LNK and SOCK) are `lstat`ed by Node inside `readdirSync({ withFileTypes: true })`, in order, and Go does the same on Linux, so a failing `lstat` is reported before the walker looks at earlier entries. Go reads `d_type` on every Unix (`ReadDirTypes`: Linux through `getdents64`, darwin and the BSDs through `os.File.ReadDir`, which takes the type from `readdir_r` or `getdirentries`), so a readable but unsearchable directory keeps its entry types as it does under libuv; where the type is unknown (`DT_UNKNOWN`, `DT_WHT` on darwin) Go's `os` `lstat`s the entry by name inside the listing, where libuv's `scandir` does not, and drops an entry that vanished between the listing and that `lstat`. Native darwin filesystems (APFS, HFS+) and Linux ones (ext4, xfs with `ftype`, btrfs, tmpfs) never report `DT_UNKNOWN`, so the difference needs NFS, FUSE, SMB or an XFS without `ftype`. An entry whose name holds a lone surrogate (Windows, WTF-16) is decoded to U+FFFD by `os`, so its later `lstat` by name fails in Go where Node's name would not exist either way on POSIX; on Windows a file with such a name is the one case Go cannot name. Directories are opened with `O_DIRECTORY` and then `fstat`ed, as glibc's `opendir` does. The `d_ino` 0 skip and the `d_type` rule were checked on FUSE (glibc 2.36 and 2.39). glibc 2.28 to 2.32 also skip, inside the `getcwd` walk only, entries whose `d_type` is neither `DT_DIR` nor `DT_UNKNOWN`; Go follows 2.33 to 2.36 there, so on Debian 11, RHEL 8 or Ubuntu 20.04 a directory in the cwd's path reported with a wrong type can make Node fail with `ENOENT` where Go finds the path. `existsSync` is `access(2)` with `F_OK` and Go's port calls `access` too, so a filesystem that answers `access` and `stat` differently gives the same answer in both. `os.tmpdir()` reads `TMPDIR`, `TMP` and `TEMP` through `SafeGetenv`, which ignores them in setuid, setgid and (on Linux) `AT_SECURE` processes unless the only permitted capability is `CAP_NET_BIND_SERVICE`; Go applies the same test (`TestLiveTmpdirSetidMatchesNode`).

## Process ids and fault-only error text

A ledger binding is staged as `.<base>.<pid>.<uuid>.tmp` next to its destination (`src/ledger-binding.ts:540`), and the pid is `fl`'s own process id, as `process.pid` is Node's. When the final rename fails (for example `EISDIR` when `--ledger-binding-output` names an existing directory), the message `rename '<dir>/.<base>.<pid>.<uuid>.tmp' -> '<dir>/<base>'` holds that pid, so stderr differs between any two runs, TS or Go; the exit status and the tree match. `TestLiveWriterFaults` masks the pid in staged names (`maskStagedPid`); no writer golden holds one.

`investigate git` and `minimize git` remove their temporary root with `fs/promises.rm`, whose callback rimraf starts on every child of a directory at once and reports whichever failure completes first; Go removes the children in name order and reports the first failure in that order. Both attempt every child, so only the message can differ, and only when two children both fail to be removed.

Stat calls follow libuv on Linux: `lstat`, `stat` and `fstat` are `statx` (with libuv's fallback to the old calls where `statx` is refused), and a directory opened for listing is checked with `fstatat(fd, "", AT_EMPTY_PATH)` as glibc 2.36's `opendir` does, so a fault injected on one stat-family syscall lands on the same step in both (round 7 #12). Other Unix systems use Go's `stat`, `lstat` and `fstat`, which are the calls libuv makes there.

## `ENOTDIR` on Windows

When a path component that should be a directory is a file (`file.json/x`), Linux reports `ENOTDIR` while Windows (libuv maps `ERROR_PATH_NOT_FOUND` to `ENOENT`) reports `ENOENT`. Go on Windows reports `ENOTDIR` in that case, deliberately: the Linux-generated goldens contain this error (`git-unbound__hashes-enotdir`, `manifest.json/x` declared in `hashes.txt`), and one expected output on every OS keeps the corpus portable. This is a deliberate divergence from TS on Windows, listed in the spec's done criteria. A missing parent directory is `ENOENT` everywhere. Listing a file (`scandir`) is `ENOTDIR` in both, because libuv's `fs__scandir` sets that code itself. All other Win32 errors follow libuv's `uv_translate_sys_error`.

## Windows paths, lstat and deletion

Go follows Node's Windows fs layer rather than Go's `os` package. Every fs call except `mkdtemp` goes through a port of Node's `ToNamespacedPath` (src/path.cc: its C++ `PathResolve`, then a `\\?\` or `\\?\UNC\` prefix), so Win32 path normalization is off as in Node: names ending in a dot or space and reserved device names (`NUL`, `CON.txt`) are ordinary files, and paths longer than `MAX_PATH` work without `LongPathsEnabled`. Error messages print the namespaced path without its prefix, as Node's `StringFromPath` does, which is the resolved absolute path rather than the path as typed. `lstat` and `stat` port libuv 1.51's `fs__stat_impl` (the open flags, the retry without `FILE_FLAG_OPEN_REPARSE_POINT` for reparse points libuv does not read as links, and the parent-directory lookup after `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION`, where any reparse point is a link to lstat), so an AF_UNIX socket or another reparse point that cannot be opened is an lstat error, and an unreadable junction is a symbolic link. `unlink` and `rmdir` port `fs__unlink_rmdir`: POSIX-semantics deletion that ignores the read-only attribute, falling back to a legacy delete only where the filesystem lacks it. None of this has been run on a Windows host; the ports were checked against the libuv and Node sources and by cross-compilation, and `toNamespacedPath` against `path.win32.toNamespacedPath` for absolute paths.

The TS bundle walkers recurse on V8's stack, so a bundle nested thousands of directories deep fails with `failed safely: Maximum call stack size exceeded`. On Linux and macOS `PATH_MAX` stops such a tree first, but Windows paths are namespaced (`\\?\`, 32,767 units), and Go's walkers have no depth limit: a bundle of a few thousand nested empty directories (about 3,700 for git, 3,900 for demo and 4,800 for prevention bundles, extrapolated from linux/arm64) is INVALID in TS and VALID in Go there. The per-level cost has not been measured on Windows, so it is not modelled.

## WSL symlinks on Windows

Go's `Lstat` follows libuv 1.52 (Node 22.23 and later): a WSL symlink (`IO_REPARSE_TAG_LX_SYMLINK`) is a symbolic link. libuv 1.51 (Node 22.22) has no case for that tag and retries with a following stat, which Win32 cannot resolve, so `lstatSync` throws. Either way the verifiers reject the file; only the error line differs.

## Memory use

Go holds a JSON input as UTF-16 while parsing it and builds one `Obj` per object, so on large JSON inputs it needs 4 to 6 times Node's memory (a 40 MB document of 5M small objects peaks at about 1.9 GB in Go against 0.5 GB in Node). Under a memory limit this can decide the outcome: in a 4 GB container a demo bundle whose `analysis.json` holds an 80 MB array is verified by TS (INVALID, with the full error list) and gets Go killed by the OOM killer (exit 137, no output). The demo verifier reads `analysis.json` without a size cap, as TS does; the git verifier's per-artifact cap of 128 MiB is too high to prevent it. Outputs are identical whenever both finish. Collation builds sort keys lazily, as far as comparisons need them, and skips the identical prefix of two keys as ICU does, so long record keys whose bytes are identical up to where they differ cost about what they cost Node (2,000 keys sharing a 3,000-character U+FDFA prefix: 0.8 s and 298 MB in Go, 0.5 s and 282 MB in TS). A sorted string keeps at most about 500 primary weights of its key; comparisons that need more (keys that differ only in case or accents early on, then tie for thousands of collation elements) build keys for that comparison alone, as ICU does. Memory then stays close to Node's (2,000 keys of `a` or `A` before the same 3,000 U+FDFA: 267 MB peak in Go, 210 MB in TS, in a container with a 163 MB baseline), but such sorts take longer (7.3 s against 2.7 s).

## Key parsing errors in `witness sign` and `witness verify --keyring`

TS parses reviewer keys with Node's `crypto.createPublicKey` / `createPrivateKey`. Go ports the whole path ncrypto and OpenSSL 3.5 take (`internal/witness`). Message and `opensslErrorStack` match Node for every algorithm OpenSSL's default provider decodes, not only the verdict. The port covers:

- **PEM reading.** The PEM layer (`PEM_read_bio_ex`, BOM and trailing-byte stripping, RFC 1421 headers, `EVP_DecodeUpdate`, `PEM_get_EVP_CIPHER_INFO`).
- **Node's control flow.** ncrypto's three public passes (`PUBLIC KEY`, `RSA PUBLIC KEY`, `CERTIFICATE`) with the private-key fallback, then `PEM_read_bio_PrivateKey`'s `OSSL_DECODER` loop and legacy reader.
- **Algorithms.** Every algorithm decoder:
  - RSA and RSA-PSS;
  - DSA, DH and DHX;
  - EC with named and explicit parameters over GF(p) and GF(2^m), and SM2;
  - X25519, X448, Ed25519 and Ed448;
  - ML-DSA and ML-KEM, including their load checks and ML-KEM's pairwise test (with a random message, as the default provider's `pct_type` "random" draws it: see below);
  - SLH-DSA.
- **DER and errors.** OpenSSL's table-driven DER decoder, and its 16-slot error queue with marks.

`TestLivePEMKeyParsing` compares about 20,000 key texts with Node: generated mutations of every algorithm, mixed multi-block texts (any algorithm, relabelled, certificates carrying every key type), the reviewers' corpora, and a targeted case for each OpenSSL reason that random inputs miss. It compares verdict, key type, message and full error stack. It matched on macOS arm64 (Node 22.23.3, OpenSSL 3.6.5) and Linux arm64 (Node 22.22.2, OpenSSL 3.5.5). What still differs:

- **An encrypted block in a public pass.** Node passes no passphrase callback there, so OpenSSL's `PEM_def_callback` opens `/dev/tty` and prompts (`Enter PEM pass phrase:`). This happens for a `PUBLIC KEY`, `RSA PUBLIC KEY` or `CERTIFICATE` block with a valid `Proc-Type: 4,ENCRYPTED` / `DEK-Info` header. Go never prompts and treats the pass as failed. Both sides do that when there is no terminal (CI, and the live test, which starts Node with `setsid` and stdin on `/dev/null`). Run interactively, TS waits for a passphrase that Go never asks for.
- **`BN_mod_sqrt`'s random search on a composite modulus.** This needs an explicit-parameter EC key with a compressed point, whose field "prime" is composite, is ≡ 1 mod 8, and has Jacobi symbol 1 for every number below 22. For such a key OpenSSL tries random candidates, and the result can change from run to run. Go reports `too many iterations`. For a prime modulus the result does not depend on the candidates, and Go matches. No real key has a composite field.
- **Random blinding over a ring that is not a field, and ML-KEM's random pairwise test.** OpenSSL never checks that an explicit binary polynomial is irreducible or that an explicit prime is prime, and Go follows its arithmetic there (`BN_GF2m_mod_inv` fails where no inverse exists, the Montgomery ladder's `cannot invert` / `ladder post failure`, the wNAF multiplication's failed inversions, hybrid-point parity). OpenSSL draws random numbers at these points:
  - `BN_GF2m_mod_inv` blinds every inversion with a random nonzero value;
  - `ladder_pre` (GF(p) and GF(2^m)) blinds the ladder's coordinates with two random nonzero elements, used when an `EC PRIVATE KEY` has no public point and OpenSSL computes priv·G;
  - `BN_GF2m_mod_solve_quad` for an even degree tries random `rho`;
  - `BN_mod_sqrt` searches for a non-residue with random candidates after the numbers below 22;
  - ML-KEM's import pairwise test (`ml_kem_pairwise_test`) encapsulates a random 32-byte message (`ossl_ml_kem_encap_rand`) to the key's public half and decapsulates it with the private half.

  On a field none of the first four changes the result, and for a consistent ML-KEM key, or one whose private vector simply does not match, the pairwise test gives the same answer for every message. Over a reducible polynomial or a composite "prime" a random value that shares a factor with the modulus can, so Node's verdict on the same text can change from run to run. So can an ML-KEM private key whose t = A·s + k·e carries a scaled error (round 10, r10-1): it passes the load checks, and decapsulation then recovers some messages and not others, so Node accepts such a key in anything from about 0.05% to 97% of runs. Each decoder attempt draws again. Go makes the same draws, through `internal/clock`: the system CSPRNG in release builds, and a stream of its own under the test seed, which leaves the seeded times, UUIDs and temp names unchanged. So on these inputs Go's result is as random as Node's, with the same distribution. A single run of each can still disagree. Cases Node gives the same way every time (for example a wNAF multiplication with about 140 blinded inversions over x^64+x^10+1, which fails every time) come out the same in Go.

  `TestLivePEMKeyParsing` compares single runs. When a case disagrees, it runs that case 400 times on each side and requires each outcome's share to agree (a two-proportion z below 5). That covers round 9's random cases, about 60 to 90 per run, including the c10, c13 and det_flip reproductions. Round 10's three noisy ML-KEM keys (testdata/pemkemnoise.json, accepted by Node in about 97%, 55% and 0.05% of runs on 3.6.5 and 3.5.5) are always compared by share, over 3,000 runs per side. No real key has such a field, and ML-KEM key generation never produces such an error.
- **OpenSSL version.** Go follows Node 22.22.2's bundled OpenSSL 3.5.5. OpenSSL 3.6.5 (a Node linked against a system OpenSSL, such as Homebrew's) differs in two places:
  - a long-form DER length with no content byte after it (`30 81 00`) is `field missing` rather than `header too long`;
  - a malformed DH PKCS#8 key reports `Diffie-Hellman routines::decode error` rather than `invalid parameter nid`.
- **Platform.** These follow the platform as OpenSSL does, so a key can be accepted on one machine and refused on another, by both implementations alike:
  - `sanitize_line` strips trailing bytes `<= ' '` as C `char`. Where `char` is signed (x86, macOS, Windows), every byte >= 0x80 also counts as whitespace, so a UTF-8 NBSP or `é` after a PEM line is ignored. Where `char` is unsigned (Linux on arm64, arm, ppc64, s390x, riscv64), it is not.
  - The AES-NI cipher names (`AES-128-CBC-HMAC-SHA1` and the like) are known in a `DEK-Info` header only on x86. That changes only which error an encrypted header gets.
  - Windows has no live oracle run.

## The judge-proof server and browser opener

`fl judge-proof` serves the page with Go's `net/http` where TS uses Node's `http`. Go sets the framing headers Node adds itself: `Connection: keep-alive` and `Keep-Alive: timeout=5` for an HTTP/1.1 request that does not ask to close, `Connection: close` otherwise (every HTTP/1.0 request included), `Transfer-Encoding: chunked` for HTTP/1.1 bodies, and no `Content-Length` (none for `HEAD` either); its `Date` uses the same format. `TestLiveJudgeServer` compares status, every header but `Date`'s value, and the body, for HTTP/1.1, `Connection: close` and HTTP/1.0 requests. What still differs on the wire: header order (Go writes them sorted, Node in insertion order); the status line's version for an HTTP/1.0 request (Node always answers `HTTP/1.1`, Go `HTTP/1.0`); chunk boundaries (Node sends the page as one chunk, Go in 2 KiB chunks); the HTTP parser's handling of malformed requests (net/http still parses the request line and the header lines). The request target: TS takes `new URL(request.url, "http://127.0.0.1").pathname`, Go approximates it for origin-form and scheme-relative targets (query and fragment dropped, `\` as `/`, a `//host` authority skipped, `.`/`..` and `%2e` segments removed), so absolute-form targets and the targets for which `new URL` throws (`//` with an empty or invalid host, which makes the TS request handler throw and Node exit) are not reproduced. Connections follow Node 22's `http.Server` defaults (`internal/proofview/server.go`): a keep-alive connection is closed 6 s after its last activity (`keepAliveTimeout` 5 s plus `keepAliveTimeoutBuffer` 1 s), also in the middle of a request body; a response is sent as soon as the headers are in, before the body; each request is framed as llhttp frames it before net/http sees it (`internal/proofview/framing.go`, round 11): an unread body of any size, Content-Length or chunked, is read and dropped and the connection kept (net/http reset it past 256 KiB), an `Expect` on an HTTP/1.1 request that matches Node's `/(?:^|\W)100-continue(?:$|\W)/i` gets `HTTP/1.1 100 Continue` before the response and any other value the empty `417 Expectation Failed` through the normal keep-alive response, a head whose URL, field names and values (a value's leading whitespace excluded) reach 16,384 bytes, or a trailer section that does, gets Node's bare `431` and is closed, chunk extensions over 16 KiB Node's `413`, and a Content-Length or Transfer-Encoding llhttp rejects Node's bare `400`. This follows Node 22.22.2; Node 22.23 also answers `431` to more than 1,000 header lines, which Go does not; and every 30 s a connection whose headers have taken over 60 s, or whose request over 300 s, gets `408 Request Timeout` and is closed. Stopping (`server.close()`) closes only the idle connections, those between two requests, at once, including one whose responses are still being written to a slow reader (Node's handler has already ended them). It then waits for every other connection, however long: a request whose body never completes ends with the 6 s timeout, but a connection that has sent nothing (a browser's preconnect, a port scanner) or only part of its headers has no timeout once the 30 s check has stopped, so fl keeps running, as Node does, until the client closes it. The signal listeners are `process.once`, so the same signal sent again during that wait ends fl by its default action, as it ends Node (two Ctrl-C), and a different second signal is consumed. TestLiveJudgeSignalStop's held-connection subtests compare these cases with Node, including when the server closes the connection. Not compared: the 30 s check's 408 (it takes 90 s; checked by hand on macOS, Go and Node both answer a silent connection at 90 s). A `--serve-ms` above 2^31-1 ms becomes 1 ms in both, but only Node prints its `TimeoutOverflowWarning` (with its pid). The browser opener is spawned as Node's `exec` does (`/bin/sh -c '<command>'`; on Windows `%ComSpec% /d /s /c "<command>"` with verbatim arguments and `windowsHide: false`, which has not been run on Windows), except that its stdin pipe is ended at once where `exec` leaves it open until fl exits. On Windows Go always uses that `cmd.exe` form; Node checks whether `comspec` names `cmd.exe` and, for another shell (PowerShell, a POSIX shell), passes `-c <command>` with quoted arguments instead, so with a non-cmd `ComSpec` the opener's command line differs.

## Created Git object masks in the writer replay (slice 4c)

The repair commands create commits, trees and blobs whose ids depend on the machine (author and committer timestamps, and the case root in the repository path). The writer replay names a loose object the case itself created by its semantic content, `<COMMIT:...>`, `<TREE:...>` or `<BLOB:...>`, in paths, stdout and file text, and it names reflog lines and the `exec:` and `run:` execution seeds (the digests `sandbox.Execute` and the repaired-run collector derive from the real policy, environment, frozen witness and worktree path) the same way. Only objects the case created are renamed: an object that existed before it, or one in the turn-snapshot store (`.git/faultline/objects`, reached through alternates), keeps its id, and author and committer names and emails, the tree, the parents and the message all stay significant; only the timestamps are normalized. Two created objects that differ only in their timestamps share a name, so the per-file diagnostics (`files`, `modes`) show one entry for them, while the tree digest keeps one line per path and so still tells one such object from two (`TestAliasedDuplicatesChangeTheTreeDigest`). A linked worktree's `gitdir` file is compared by its masked text, never skipped. The only Git-version exception is the EMPTY directory `.git/worktrees/<name>/refs` that Git 2.54 creates and the pinned 2.39.5 does not; a non-empty one, a file or a symlink of that name stays compared (`TestWorktreeRefsExclusionIsNarrow`). The masks live in `difftest/gen/gen-writers.ts` and `difftest/writer_test.go`; slices 4a and 4b add their own `<COMMIT>` rule and the controller merges the entries into one.

## Live repair brief HTTP (`fl repair brief --live`, slice 4c)

`proposeRepairBriefWithGpt` posts with Node's `fetch` (undici); Go has its own client (`internal/repair/live.go`) that reproduces undici's request and the outcomes the CLI prints, and `TestLiveProposeRepairBrief` compares 260 generated replies against Node for the request bytes (the five headers undici adds, the body) and the result or error text. What still differs:

- TLS roots: Node verifies with its bundled Mozilla roots (and `NODE_EXTRA_CA_CERTS`), Go with the system pool (`SSL_CERT_FILE`, `SSL_CERT_DIR`). A host whose system store lacks a root Node bundles, or the reverse, fails with `fetch failed` on one side only.
- `Accept-Encoding`: to an https URL undici sends `br, gzip, deflate`; Go sends `gzip, deflate`, because the module has no Brotli decoder. A `br` coding in a reply ends as `terminated` in Go where Node decodes it; OpenAI does not send `br` unless asked. To an http URL both send `gzip, deflate`. The gzip and deflate decoders are Go's own (`internal/repair/inflate.go`, zlib's streaming semantics: 0 of 32,582 disagreements with zlib 1.3.1, where `compress/flate` was short on 26% of truncated streams).
- Proxies: Node 22 honours `NODE_USE_ENV_PROXY` with `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY`; Go ignores them. Behind a mandatory proxy Go fails with `fetch failed` where Node connects through it.
- The `Location` of a redirect is parsed by WHATWG URL in Node and by `url.Parse` in Go; hosts, ports and percent-encoding the two parse differently follow different redirects. Credentials in `Location`, a non-HTTP scheme and a loop past 20 hops are `fetch failed` in both.
- Header size: undici's limit on a response head counts bytes in its own way; Go's `MaxResponseHeaderBytes` counts the head differently at the edge, so a head within a few bytes of the cap is accepted by one and not the other.
- Every network error before the response headers (DNS, refused, TLS, a reset, a malformed status line) is `fetch failed` in both; undici's `cause` differs and is not printed. A body read error after the headers is `terminated` in both. The 300 s body timeout resets on each read, as undici's idle timeout does; no test reaches it.
- The base URL override `FAULTLINE_TEST_OPENAI_URL` exists only in `faultline_test` builds (`internal/repair/openai_test_url.go`); the `go` CI job checks that the untagged release binary does not contain the name.

## Identity-less `commit-tree` (slice 4c)

The repair commands commit the repaired worktree with `git commit-tree`. With no `user.name` and `user.email` configured, git's error names the machine (`unable to auto-detect email address (got 'user@host.(none)')`), so that text differs between any two hosts, TS or Go. The writer scenarios configure an identity (`REPAIR_CONFIG`). `TestLiveCommitRepairedWorktreeState` runs identity-less repositories too and requires the thrown texts to be equal, which holds because both sides run on the same host; a golden of that failure would differ between machines, so none exists.

## `cpSync` is a Linux model (slice 4c)

`fl repair` copies the proof bundle with `fs.cpSync`, which in Node 22.22.2 is a C++ function over `std::filesystem`. `nodefs.CpSyncTree` models the libstdc++ behaviour (directories get the default mode with the umask and no `chmod`; the C++ aborts print libstdc++'s terminate text), and `TestLiveCpSyncTree` compares it with Node on Linux only. On macOS libc++ applies the umask to nested files (Go keeps the source mode) and its abort text is libc++abi's; on Windows the MSVC STL's texts, exit code and `\` separators differ. The success path is assumed to match there; the `cpSync` abort cases are not modelled off Linux.

## Oracle pathologies not reproduced

- ICU 78's discontiguous-contraction back-off can loop forever: a TRAILING_CCC contraction starter, an out-of-order run with a supplementary mark, U+0344 and a starter (`ا\u{11100}\u{16AF2}\u{0344}ꪫ` against the same string without the last code point) make ICU's iterator step back past the starter and re-read it. Go ports the iterator and hangs the same way on the same pairs. Once memory runs out, ICU's CE buffer allocation fails and `localeCompare` returns an arbitrary sign, while Go dies of out-of-memory (exit 2).
- Loading `dist/cli.js` instantiates undici's WebAssembly HTTP parser, which reserves about 10 GiB of address space: under `ulimit -v` of about 11 GiB or less (the last failing limit is 11,048 MiB on glibc linux/arm64 and 10,669 MiB on musl), TS prints the verdict and then exits 1 with `RangeError: WebAssembly.instantiate(): Out of memory`, where Go exits with the verdict's status.
- On macOS, Node links CoreFoundation, which sets `__CF_USER_TEXT_ENCODING=0x<uid>:0x0:0x0` in Node's environment when it is missing, invalid or belongs to another uid: when it is missing git sees it under TS only, and when it is invalid git sees the inherited value under Go and the replaced one under TS. Git's output does not depend on it.

## Oversized `.faultlineignore` rules (V8 limit, not reproduced)

TS turns each `.faultlineignore` line into a `RegExp` with flag `i` (`src/turn-snapshot.ts:401`), and V8 compiles it on first use. A line with more than 32,767 code units of fixed-width text in a row (literals and `?`), or roughly 1,300 `*`/`**` wildcards, makes that compilation throw `Invalid regular expression: /…/i: Regular expression too large` or `… Stack overflow`. Whether it throws can depend on the path being tested: for example, V8 skips code generation for a pattern of non-Latin-1 literals when the path is one-byte. Go matches these rules like any other (`internal/turnsnap/ignore.go` runs a set-of-states scan with the same JS semantics: ECMAScript case folding without `u`, `.` excluding line terminators, last match wins). So where TS fails the turn snapshot, Go applies the rule. Such lines need several kilobytes on one line, inside a file capped at 256 KiB.
