# Known differences between Go `fl` and frozen TS (`faa98c0`)

Every intentional divergence is listed here. Anything not listed is a bug.

## Locale-dependent key order (TS bug, not reproduced)

TS `canonicalJson` sorts object keys with `localeCompare`, which uses the machine's ICU default locale. Under `sv-SE`, Node sorts `å ä ö` after `z`; under `tr-TR`, it orders `I` before `i`. Go always uses the en-US (CLDR root) order that CI and `C.UTF-8` machines produce. Bundles written under an affected locale with affected keys already fail TS verification on en-US machines.

Go's collation (`internal/collation`) is generated from the ICU 78 root collation data (Unicode 17, CLDR 48) that official Node 22 builds ship from 22.22.1 on, and follows ICU's comparison, not a plain UCA key compare: `internal/collation/iter.go` ports ICU's `FCDUTF16CollationIterator` and `CollationIterator` (incremental FCD check, contraction and discontiguous-contraction matching with its look-ahead and backtracking, prefix contexts), so mark runs that ICU leaves un-normalized after contraction look-ahead collate as in ICU; ICU's contraction and prefix data (U+FDD0 rows excluded as genuca does); and `RuleBasedCollator::doCompare`'s identical-prefix skip and early exit at the first primary difference. The identical-prefix skip makes `localeCompare` non-transitive on some inputs, so `SortLocale` runs a port of V8's TimSort. Parity is checked against Node by `TestLiveCollationAllCodePoints` (every code point), `TestLiveCollationRules` (every contraction and prefix key with inserted, reordered and dropped marks and U+FDD0/U+FDD1 sequences), `TestLiveCollationMarkRuns` (contraction starters followed by supplementary and BMP mark runs, each string against its NFD and NFC forms, reorderings and shared prefixes) and `TestLiveSortLocale`.

**Minimum Node version.** Earlier Node 22 releases bundled ICU 74 (22.0), 75.1 (22.1) and 76/77 before ICU 78. Bundles written by those releases whose overlay paths or JSON keys contain characters assigned after their Unicode version (for example U+1FAE9, Unicode 16) may use an order Go rejects (`overlay records are not in canonical path order`, or a different canonical-JSON digest). Current Node 22 TS agrees with Go. A Node built against a system ICU (`--with-intl=system-icu`) can differ the same way.

## Directory listing order on Windows

Node's `readdirSync` returns byte-sorted names on Linux and macOS but filesystem order on Windows (NTFS: case-insensitive upcase order). Go returns byte-sorted names everywhere, so Go on Windows matches TS on Linux. This affects the order of error lines that enumerate files, and, because the file walkers stop at the first symlink, special file or oversized file they meet, which file such an error names when a bundle has two offending entries (for example `analysis.json` before `ROOT.sha256` on NTFS, the reverse in byte order).

## Git's default object format

Not an output difference, but an environment dependency of both implementations. The verifier creates its temporary repository with a plain `git init --bare` (`src/git-proof-bundle.ts:931`), which follows `GIT_DEFAULT_HASH` and `init.defaultObjectFormat`. A SHA-1 bundle therefore verifies only where git defaults to SHA-1, and a SHA-256 bundle only where it defaults to SHA-256; elsewhere both report `Git bundle extraction failed`. Go runs the same git commands and matches TS in both settings. The golden generator and replay pin `GIT_DEFAULT_HASH=sha1`, and the `git-sha256` base runs with `GIT_DEFAULT_HASH=sha256` (`difftest/testdata/base-env.json`).

## V8 limits

When a zod schema rejects a deeply nested value, TS builds the error text with `JSON.stringify(issues, replacer, 2)` (the `ZodError.message` getter). V8 does this recursively, and past its native stack limit it throws `RangeError: Maximum call stack size exceeded`, which the verifier's catch prints as a `failed safely` line. Go models V8's stack use (`internal/jsjson/stack.go`): each non-empty array or object pushes a frame, empty containers and primitives push none, and objects on V8's slow path (array-index keys, or 128 or more members, which JSON.parse builds in dictionary mode) cost more. The model is fitted per platform and per call site (demo, prevention, git, the git lifecycle ledger, and the demo witness artifact, whose messages are read from deeper JS frames). On Node 22.22.2 linux/amd64 (glibc) it reproduces every measured threshold at every site exactly: the demo verifier still prints the zod message for 2,233 nested arrays, 4,166 single-key objects, 2,232 index-keyed objects or 2,906 alternating arrays and objects, and one more level overflows. The witness site gives 2,232 / 4,164 / 2,231 / 2,905. darwin/arm64 and linux/arm64 are fitted to Node 22.22.2 too (the release CI pins), from the stack-live CI job's measurements at all five sites, and `TestLiveStackThresholdsMatchNode` bisects every site and shape against `node dist/cli.js verify` on linux/amd64, linux/arm64 and darwin/arm64 in CI. On darwin/arm64, values that mix shapes on the way down (alternating index-keyed and named objects, or array, named and index-keyed objects in turn) at the demo site overflow one level later in TS than the model predicts (3,536 vs 3,535 and 3,162 vs 3,161): the per-frame costs are fitted to the pure shapes, and the rounding adds up differently on mixed ones. Dictionary mode follows V8's JSON.parse: an object literal with 128 or more named entries, duplicate keys included and index keys excluded, is on the slow path. Other builds are not fitted: musl builds (node:alpine) cost differently from glibc on the same architecture (linux/amd64 Node 22.22.2 musl: arrays 2,155, alternating 2,840, index-keyed 2,231; glibc 2,233, 2,906, 2,232; linux/arm64 differs by up to 78 levels), the stack costs drift between Node releases (darwin/arm64 prints 2,610 nested arrays on 22.22.2 and 2,747 on 22.23.2; linux/arm64 1,781 on 22.13.1 and 1,827 on 22.22.2), and Windows and other targets use the Linux model for their architecture. On those, TS can overflow tens to hundreds of levels earlier or later than Go predicts. `--stack-size` also moves V8's limit. `JSON.parse` is iterative on both sides and has no depth limit.

Go also reproduces V8's other size limits: strings longer than 0x1fffffe8 UTF-16 units (`RangeError: Invalid string length`, from `JSON.stringify`, every error message that embeds input, which Go builds with `jsexc.Concat` where TS uses a template literal, and the CLI's error join), Sets and Maps with more than 2^24 entries (`RangeError: Set maximum size exceeded` / `Map maximum size exceeded`, at the Go ports of the TS Sets and Maps, all of which are built before any comparison as in TS), and argument spreads (`errors.push(...list)`, `files.push(...collectFiles(...))`), which throw `Maximum call stack size exceeded` once the list passes V8's stack. The limits were bisected exactly through `node dist/cli.js verify` on Node 22.22.2: the demo walker passes 125,576 files one directory below the bundle root on linux/amd64 (31 fewer per further level), 110,189 on linux/arm64 and 110,181 on darwin/arm64 (32 fewer per level); git semantics errors 125,587 / 110,201 / 110,193; lifecycle-ledger errors 125,562 / 110,175 / 110,167. Node built on musl overflows about 20 elements earlier on linux/arm64, windows/arm64 uses the linux/arm64 values and other targets the linux/amd64 ones without having been measured. Node 22's `rmSync(path, { recursive: true })` is the recursive JS `rimrafSync`, so removing the git verifier's temporary bare repository overflows V8's stack when it holds an entry more than 1,672 levels deep on linux/amd64 or 1,375 on linux/arm64 (Node 22.22.2, glibc and musl; a file and an empty directory count alike), for example from a deep global `init.templateDir` or a hook. Go's rimraf throws the same `Maximum call stack size exceeded` at that depth and leaves the tree behind as TS does; darwin cannot reach the depth (PATH_MAX). `TestLiveSpreadLimitsMatchNode` and `TestLiveRimrafDepthMatchesNode` check these limits against Node on linux/amd64, linux/arm64 and darwin/arm64 in CI. Some allocations make V8 abort the process, and Go aborts the same way. JSON.parse arrays of 2^27 or more elements print the V8 fatal-error header with the real length (`# Fatal JavaScript invalid size error 134217729 (see crbug.com/1201626)`) and die by SIGTRAP (exit 133). An object's index-keyed entries (duplicates included) go into a NumberDictionary when that is smaller than a FixedArray up to the largest index (V8's `ShouldConvertToSlowElements`: 9 × the dictionary capacity for the entry count, at most the largest index + 1), otherwise into that FixedArray: a FixedArray of 2^27 or more slots aborts the same way without the crbug note (`{"0":0, …5,592,406 entries…, "134217727":0}`), and a dictionary of 22,369,622 or more entries fails like a NameDictionary of 22,369,622 or more named entries (duplicates included): Node's `FATAL ERROR: invalid table size Allocation failed - JavaScript heap out of memory` report and SIGABRT (exit 134). `String.prototype.split` into 2^27 or more parts aborts like the FixedArray (a demo `hashes.txt` of 134,217,728 lines or more). Go builds the object before it aborts where V8 aborts while sizing it, so under a memory limit that Node's peak fits in (about 2 GB for 22,369,622 named keys) Go can be killed by the OOM killer (exit 137, no output) instead. Node's GC trace, native stack trace and `#FailureMessage Object` address are not reproduced. A utf8 read of a file of 0x1fffffe8 bytes or more fails with `Cannot create a string longer than 0x1fffffe8 characters` in both; Node reads the whole file before checking, so under a memory limit smaller than the file TS is killed by the OOM killer (exit 137, no stdout) where Go, which checks the size first, prints the error.

## Stdout write errors

Go builds stdout the way Node's `createWritableStdioStream` does, from a port of libuv's `uv_guess_handle`. A regular file or character device is a `SyncWriteStream`: one `write(2)` per chunk, a short count ignored (a full disk or `RLIMIT_FSIZE` reached in the middle of a chunk truncates the output silently), and a failing call reported as `Error: <CODE>: <description>, write` (`/dev/full` gives `Error: ENOSPC: no space left on device, write`). A pipe, stream socket or terminal is a libuv stream: everything is written, waiting while the descriptor would block (for example after another process set `O_NONBLOCK` on a shared pipe), and a failure is `Error: write <CODE>`. UDP sockets and handles libuv cannot classify (a datagram Unix socket, a directory) get Node's dummy writer, which discards the output. As in Node, stdout is classified on first use (the first write, after the checks), so a terminal that hangs up during verification gets the file form, and a terminal, pipe or FIFO that fd 1 has open read-only is a stream libuv cannot write to, which fails with `Error: write EPIPE` without a write. Both runtimes ignore SIGPIPE, so a pipe whose reader has gone is `Error: write EPIPE`, and any stdout write error exits 1. On Windows, Node writes pipes synchronously, so a pipe error has the file form, `ERROR_BROKEN_PIPE` and `ERROR_NO_DATA` are `EPIPE`, and a handle not opened for writing is `EBADF` (`fs__write` turns `ERROR_ACCESS_DENIED` into `ERROR_INVALID_FLAGS`), as in libuv. On a stream, `ENOBUFS` waits like `EAGAIN`, and on macOS `EPROTOTYPE` is `ECONNRESET`, as in `uv__try_write`. Error codes come from libuv's full `uv_err_name` table; an errno it cannot name is `Unknown system error -N` in both forms, as in every error Node throws from C++ (the fs calls and `uv_cwd` included). Node reports the error as an unhandled `'error'` event, a stack trace around the error line; Go prints the error line only. `TestLiveStdoutMatchesNode` compares these cases with Node on Linux. One oracle pathology is not reproduced: when stdout is a pseudo-terminal whose master has already closed, Node blocks forever in `uv_tty_init` reopening the terminal; Go reports `Error: write EIO` and exits 1.

## Signals and resource limits

Node resets signals 1 to 31 to their default action at startup, ignoring only SIGPIPE and SIGXFSZ, clears the signal mask, and raises its soft `RLIMIT_NOFILE` to the hard limit; libuv resets every signal and the mask in the processes it starts, which inherit the raised limit. Go emulates this from the first package initialized (`internal/boot`). On Linux the signals whose default action ends the process (HUP, INT, QUIT, ABRT, USR2, ALRM, TERM, STKFLT, XCPU, VTALRM, IO, PWR, SYS and the real-time signals from 35) are set to SIG_DFL in the kernel; externally sent SEGV, BUS, FPE, ILL and TRAP are caught and end `fl` by their default action (the Go runtime keeps its handler so that faults in Go code still panic); inherited SIG_IGN on TSTP, TTIN, TTOU and CONT is reset; and then an inherited signal mask is cleared by re-executing `/proc/self/exe` once with an empty mask, before the standard descriptors are marked close-on-exec, so a signal left pending under the mask takes its default action as it does in Node and the output reaches the same descriptors. Deaths go through `rt_sigaction`, `rt_sigprocmask` and `tgkill` on the dying thread, with core dumps where the kernel makes them. The soft `RLIMIT_NOFILE` is raised as Node raises it and git inherits it. `TestLiveSignalsMatchNode` compares the death, the output, and git's signal mask, ignored set and descriptor limit with Node on Linux, including a blocked mask, a signal pending under it, and a low soft limit.

On macOS the same signals are caught through os/signal and `fl` dies by re-executing `/bin/sh -c 'kill -N $$'`, since the syscall package exports no `sigaction` or `sigprocmask` there. `fl` stops writing and does not exit once a signal has reached it, but Go learns of a signal on a goroutine, a few milliseconds after Node would have died, so a signal that arrives as verification ends can still let the report out first. A mask or SIG_IGN on the stop signals inherited from the parent stays in effect on macOS, and a `/bin/sh` that ignores SIGQUIT (bash) exits 131 instead. macOS delivers SIGBUS, SIGILL and SIGEMT sent with `kill` (and at times SIGSEGV) with a fault code rather than the code of a user-sent signal, so the Go runtime takes them for a crash in `fl` and exits 2 with a goroutine dump where Node dies by the signal.

Remaining differences on every Unix system: a signal that arrives before the Go runtime has initialized any package (under a millisecond on an idle machine, over 10 ms on a heavily loaded one) is handled by the runtime (ALRM, USR2 and the like are dropped, QUIT and ABRT dump goroutines); SIGPROF is consumed by the Go runtime, so it doesn't stop `fl`; SIGUSR1 starts Node's inspector (a "Debugger listening" line on stderr) and is ignored by Go. On Linux, a real-time signal (35 to 64) inherited as SIG_IGN stays ignored in Node and in its git, while `fl` sets it to SIG_DFL: the Go runtime has replaced the inherited disposition with its own handler before any package initializes and keeps the original out of reach. If the re-execution fails (a binary on a `noexec` mount), `fl` continues with the inherited mask, and git inherits it too. On Windows, console control events follow the Go runtime.

Node keeps a few dozen file descriptors open for its event loop, thread pool, V8 platform threads and module loading. With a hard `RLIMIT_NOFILE` below 31, TS fails where Go still verifies (from 15): Node 22.22.2 on Linux prints `spawnSync git EMFILE` with 20 to 30 descriptors (on 1, 4 and 6 CPUs alike), fails to load one of its own modules with `EMFILE` at 18, and aborts in `uv_loop_init` at 16 or fewer. The numbers change between Node versions, so they are not modelled.

## Starting git

`spawnSync` is ported from libuv and the C library Node's official builds use. On Linux the executable lookup is glibc's `execvp` (a candidate that fails with `ENOEXEC`, such as a script without a `#!` line, is run by `/bin/sh`; `ESTALE`, `ENODEV` and `ETIMEDOUT` move on to the next PATH entry; a PATH entry of 4,096 bytes or more is skipped and the bare name is tried in the working directory next; the default search path is `/bin:/usr/bin`); on macOS it is libuv's own search over `posix_spawn`. Child sockets get libuv's 64 KiB buffers, descriptors 0 to 15 and the run above them are close-on-exec from startup (`uv_disable_stdio_inheritance`), environment names that are array indices (and, on Linux, the empty name) are dropped as `{...process.env}` drops them, and an errno libuv has no name for prints as `Unknown system error -N`. On Windows git is created with `CREATE_NO_WINDOW`, in a kill-on-close job object, with 64 KiB pipes, without the hidden `=X:` variables, and with an 8.3 working directory when the cwd is `MAX_PATH` or longer. Remaining differences: when every PATH entry is skipped for length, glibc reports whatever errno was left over in the child (`EINVAL` or `ENOSYS` depending on the host), and Go reports `ENOENT`; Node built on musl (Alpine) has musl's `execvp`, which does not run `ENOEXEC` files through `/bin/sh` and searches `/usr/local/bin:/bin:/usr/bin` by default; on macOS, Go starts git with fork and exec rather than `posix_spawn`, so a malformed Mach-O fails with `exit null` instead of `Unknown system error -85` (EBADEXEC), and libuv aborts Node outright when every PATH entry is too long; Go on Windows passes the environment block unsorted.

## Working directory errors and the C library

`process.cwd()` is libuv's `uv_cwd` over the C library's `getcwd`, and its error codes come from that library. Go ports glibc's `getcwd` on Linux (the `getcwd` syscall, then `__getcwd_generic`'s walk up through `..` when the kernel cannot return the path: longer than a page, or outside the process root after `chroot(2)`) and Apple Libc's on macOS (the `F_GETPATH` fast path checked against `.`, then the same kind of walk, keeping the first `fstatat` error), with `uv_cwd`'s retry that turns a path exactly one byte too long into `ENOBUFS`. `TestLiveCwdErrorsMatchNode` compares `verify` from deleted, recreated, over-long (short and long segments around 4,096 bytes), unreadable and chrooted working directories with Node on Linux. musl (Alpine) has no fallback walk: a cwd longer than a page gives `ENAMETOOLONG` and a cwd outside the root gives `ENOENT` there, where Go, like glibc Node, gives `ENOBUFS`/`ERANGE` and the real path. The macOS port has not been run here (the reviewers' macOS cases were checked against Apple's source). Other Unix systems use Go's `getcwd`.

## Directory listings on Linux

Node's `readdirSync` is libuv's `scandir`, which reads entries through the C library's `readdir`. glibc 2.28 to 2.36 (Debian 11 and 12, RHEL 8 and 9, Ubuntu 22.04) skips entries whose inode number is 0, which some FUSE filesystems and old XFS report for live files; glibc 2.37 and later and musl list them. One static binary cannot follow both, so Go follows glibc 2.36, the C library most LTS systems run Node on, in the bundle walkers, rimraf and the `getcwd` walk: on glibc 2.37+ or musl hosts with such a filesystem, Node sees files Go does not. Entries whose type the filesystem does not report (`DT_UNKNOWN`: XFS without `ftype`, some NFS and FUSE) are `lstat`ed by Node inside `readdirSync({ withFileTypes: true })`, in order, and Go does the same on Linux, so a failing `lstat` is reported before the walker looks at earlier entries; on other Unix systems Go does not read `d_type` and such a failure is reported when the walker reaches the entry. Directories are opened with `O_DIRECTORY`, as `opendir` does. This behaviour was checked against the glibc and libuv sources, not on such a filesystem.

## `ENOTDIR` on Windows

When a path component that should be a directory is a file (`file.json/x`), Linux reports `ENOTDIR` while Windows (libuv maps `ERROR_PATH_NOT_FOUND` to `ENOENT`) reports `ENOENT`. Go on Windows reports `ENOTDIR` in that case, deliberately: the Linux-generated goldens contain this error (`git-unbound__hashes-enotdir`, `manifest.json/x` declared in `hashes.txt`), and one expected output on every OS keeps the corpus portable. This is a deliberate divergence from TS on Windows, listed in the spec's done criteria. A missing parent directory is `ENOENT` everywhere. All other Win32 errors follow libuv's `uv_translate_sys_error`.

## Windows paths, lstat and deletion

Go follows Node's Windows fs layer rather than Go's `os` package. Every fs call except `mkdtemp` goes through a port of Node's `ToNamespacedPath` (src/path.cc: its C++ `PathResolve`, then a `\\?\` or `\\?\UNC\` prefix), so Win32 path normalization is off as in Node: names ending in a dot or space and reserved device names (`NUL`, `CON.txt`) are ordinary files, and paths longer than `MAX_PATH` work without `LongPathsEnabled`. Error messages print the namespaced path without its prefix, as Node's `StringFromPath` does, which is the resolved absolute path rather than the path as typed. `lstat` and `stat` port libuv 1.51's `fs__stat_impl` (the open flags, the retry without `FILE_FLAG_OPEN_REPARSE_POINT` for reparse points libuv does not read as links, and the parent-directory lookup after `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION`, where any reparse point is a link to lstat), so an AF_UNIX socket or another reparse point that cannot be opened is an lstat error, and an unreadable junction is a symbolic link. `unlink` and `rmdir` port `fs__unlink_rmdir`: POSIX-semantics deletion that ignores the read-only attribute, falling back to a legacy delete only where the filesystem lacks it. None of this has been run on a Windows host; the ports were checked against the libuv and Node sources and by cross-compilation, and `toNamespacedPath` against `path.win32.toNamespacedPath` for absolute paths.

## WSL symlinks on Windows

Go's `Lstat` follows libuv 1.52 (Node 22.23 and later): a WSL symlink (`IO_REPARSE_TAG_LX_SYMLINK`) is a symbolic link. libuv 1.51 (Node 22.22) has no case for that tag and retries with a following stat, which Win32 cannot resolve, so `lstatSync` throws. Either way the verifiers reject the file; only the error line differs.
