# Known differences between Go `fl` and frozen TS (`faa98c0`)

Every intentional divergence is listed here. Anything not listed is a bug.

## Locale-dependent key order (TS bug, not reproduced)

TS `canonicalJson` sorts object keys with `localeCompare`, which uses the machine's ICU default locale. Under `sv-SE`, Node sorts `å ä ö` after `z`; under `tr-TR`, it orders `I` before `i`. Go always uses the en-US (CLDR root) order that CI and `C.UTF-8` machines produce. Bundles written under an affected locale with affected keys already fail TS verification on en-US machines.

Go's collation (`internal/collation`) is generated from the ICU 78 root collation data (Unicode 17, CLDR 48) that official Node 22 builds ship from 22.22.1 on, and follows ICU's comparison, not a plain UCA key compare: `internal/collation/iter.go` ports ICU's `FCDUTF16CollationIterator` and `CollationIterator` (incremental FCD check, contraction and discontiguous-contraction matching with its look-ahead and backtracking, prefix contexts), so mark runs that ICU leaves un-normalized after contraction look-ahead collate as in ICU; ICU's contraction and prefix data (U+FDD0 rows excluded as genuca does); and `RuleBasedCollator::doCompare`'s identical-prefix skip and early exit at the first primary difference. The identical-prefix skip makes `localeCompare` non-transitive on some inputs, so `SortLocale` runs a port of V8's TimSort. Parity is checked against Node by `TestLiveCollationAllCodePoints` (every code point), `TestLiveCollationRules` (every contraction and prefix key with inserted, reordered and dropped marks and U+FDD0/U+FDD1 sequences), `TestLiveCollationMarkRuns` (contraction starters followed by supplementary and BMP mark runs, each string against its NFD and NFC forms, reorderings and shared prefixes) and `TestLiveSortLocale`.

**Minimum Node version.** Earlier Node 22 releases bundled ICU 74 (22.0), 75.1 (22.1) and 76/77 before ICU 78. Bundles written by those releases whose overlay paths or JSON keys contain characters assigned after their Unicode version (for example U+1FAE9, Unicode 16) may use an order Go rejects (`overlay records are not in canonical path order`, or a different canonical-JSON digest). Current Node 22 TS agrees with Go. A Node built against a system ICU (`--with-intl=system-icu`) can differ the same way.

## Directory listing order on Windows

Node's `readdirSync` returns byte-sorted names on Linux and macOS but filesystem order on Windows (NTFS: case-insensitive upcase order). Go returns byte-sorted names everywhere, so Go on Windows matches TS on Linux. This affects the order of error lines that enumerate files, and, because the file walkers stop at the first symlink, special file or oversized file they meet, which file such an error names when a bundle has two offending entries (for example `analysis.json` before `ROOT.sha256` on NTFS, the reverse in byte order).

## Git's default object format

Not an output difference, but an environment dependency of both implementations. The verifier creates its temporary repository with a plain `git init --bare` (`src/git-proof-bundle.ts:931`), which follows `GIT_DEFAULT_HASH` and `init.defaultObjectFormat`. A SHA-1 bundle therefore verifies only where git defaults to SHA-1, and a SHA-256 bundle only where it defaults to SHA-256; elsewhere both report `Git bundle extraction failed`. Go runs the same git commands and matches TS in both settings. The golden generator and replay pin `GIT_DEFAULT_HASH=sha1`, and the `git-sha256` base runs with `GIT_DEFAULT_HASH=sha256` (`difftest/testdata/base-env.json`).

## V8 limits

When a zod schema rejects a deeply nested value, TS builds the error text with `JSON.stringify(issues, replacer, 2)` (the `ZodError.message` getter). V8 does this recursively, and past its native stack limit it throws `RangeError: Maximum call stack size exceeded`, which the verifier's catch prints as a `failed safely` line. Go models V8's stack use (`internal/jsjson/stack.go`): each non-empty array or object pushes a frame, empty containers and primitives push none, and objects on V8's slow path (array-index keys, or 128 or more members, which JSON.parse builds in dictionary mode) cost more. The model is fitted per platform and per call site (demo, prevention, git, the git lifecycle ledger, and the demo witness artifact, whose messages are read from deeper JS frames). On Node 22.22.2 linux/amd64 (glibc) it reproduces every measured threshold at every site exactly: the demo verifier still prints the zod message for 2,233 nested arrays, 4,166 single-key objects, 2,232 index-keyed objects or 2,906 alternating arrays and objects, and one more level overflows. The witness site gives 2,232 / 4,164 / 2,231 / 2,905. darwin/arm64 (Node 22.23.2) and linux/arm64 (Node 22.13.1, glibc) are fitted to the reviewers' measurements at the same sites; the linux/arm64 ledger site has not been measured and uses the git offset. Dictionary mode follows V8's JSON.parse: an object literal with 128 or more named entries, duplicate keys included and index keys excluded, is on the slow path. Other builds are not fitted: musl builds (node:alpine) cost differently from glibc on the same architecture (linux/amd64 Node 22.22.2 musl: arrays 2,155, alternating 2,840, index-keyed 2,231; glibc 2,233, 2,906, 2,232; linux/arm64 differs by up to 78 levels), the stack costs drift between Node releases (linux/arm64 22.13.1 vs 22.22.2 vs 22.23.2), and Windows and other targets use the Linux model for their architecture. On those, TS can overflow tens to hundreds of levels earlier or later than Go predicts. `--stack-size` also moves V8's limit. `JSON.parse` is iterative on both sides and has no depth limit.

Go also reproduces V8's other size limits: strings longer than 0x1fffffe8 UTF-16 units (`RangeError: Invalid string length`, from `JSON.stringify`, every error message that embeds input, which Go builds with `jsexc.Concat` where TS uses a template literal, and the CLI's error join), Sets and Maps with more than 2^24 entries (`RangeError: Set maximum size exceeded` / `Map maximum size exceeded`, at the Go ports of the TS Sets and Maps, all of which are built before any comparison as in TS), and argument spreads (`errors.push(...list)`, `files.push(...collectFiles(...))`), which throw `Maximum call stack size exceeded` once the list passes V8's stack: on linux/amd64 125,607 − 31·d files for the demo walker d directories below the bundle root, 125,587 git semantics errors and 125,562 lifecycle-ledger errors, each bisected exactly; darwin/arm64 scales these by the plain-Node spread limit measured there (110,423 vs 125,273), and linux/arm64 uses the linux/amd64 values. Node 22's `rmSync(path, { recursive: true })` is the recursive JS `rimrafSync`, so removing the git verifier's temporary bare repository overflows V8's stack when it holds a directory more than 1,672 levels deep (linux/amd64, Node 22.22.2; 1,361 to 1,379 on linux/arm64), for example from a deep global `init.templateDir`. Go's rimraf throws the same `Maximum call stack size exceeded` at that depth and leaves the tree behind as TS does. The linux/arm64 value is the middle of the reviewers' range (1,370), darwin cannot reach the depth (PATH_MAX), and a leaf file rather than a directory at the boundary may shift TS's limit by one level. Two JSON.parse limits make V8 abort the process: arrays of 2^27 or more elements, where Go prints the V8 fatal-error header with the real length (`# Fatal JavaScript invalid size error 134217729`) and dies by SIGTRAP (exit 133), and objects with 22,369,622 or more named entries (duplicates included), where V8's NameDictionary cannot be allocated and Go prints Node's `FATAL ERROR: invalid table size Allocation failed - JavaScript heap out of memory` report and dies by SIGABRT (exit 134). Node's GC trace, native stack trace and `#FailureMessage Object` address are not reproduced. A utf8 read of a file of 0x1fffffe8 bytes or more fails with `Cannot create a string longer than 0x1fffffe8 characters` in both; Node reads the whole file before checking, so under a memory limit smaller than the file TS is killed by the OOM killer (exit 137, no stdout) where Go, which checks the size first, prints the error.

## Stdout write errors

Both runtimes ignore SIGPIPE, so writing to a stdout pipe whose reader has gone is an `EPIPE` write error, and any stdout write error exits 1. Node reports it as an unhandled `'error'` event: a stack trace plus the error line. Go prints only the error line, in Node's form: `Error: <CODE>: <description>, write` when stdout is a file or a non-terminal device (`/dev/full` gives `Error: ENOSPC: no space left on device, write`), and `Error: write <CODE>` for a pipe, socket or terminal. On Windows, `ERROR_BROKEN_PIPE` and `ERROR_NO_DATA` are `EPIPE`, as in libuv. Stdout and the exit code match; the stack trace lines do not.

## Signals and resource limits

Node resets every signal to its default action at startup, ignoring only SIGPIPE and SIGXFSZ, and clears the signal mask; libuv resets every signal in the processes it starts. Go emulates this from the first package initialized (`internal/boot`): on Linux the signals whose default action ends the process (HUP, INT, QUIT, ABRT, USR2, ALRM, TERM, STKFLT, XCPU, VTALRM, IO, PWR, SYS and the real-time signals from 35) are set to SIG_DFL in the kernel, externally sent SEGV, BUS, FPE, ILL and TRAP are caught and end `fl` by their default action (the Go runtime keeps its handler so that faults in Go code still panic), an inherited signal mask is cleared by re-executing `fl` once, and inherited SIG_IGN on TSTP, TTIN, TTOU and CONT is reset, so `fl` and git see the same dispositions and mask as under Node. Deaths go through `rt_sigaction`, `rt_sigprocmask` and `tgkill` on the dying thread, with core dumps where the kernel makes them. On macOS the same signals are caught through os/signal and `fl` dies by re-executing `/bin/sh -c 'kill -N $$'`, since the syscall package exports no `sigaction` or `sigprocmask` there: a mask or SIG_IGN on the stop signals inherited from the parent stays in effect on macOS, and a `/bin/sh` that ignores SIGQUIT (bash) exits 131 instead. Remaining differences: a signal that arrives in the first ~0.7 ms, before the Go runtime has initialized any package, is handled by the runtime (ALRM, USR2 and the like are dropped, QUIT and ABRT dump goroutines); SIGPROF is consumed by the Go runtime, so it doesn't stop `fl`; SIGUSR1 starts Node's inspector (a "Debugger listening" line on stderr) and is ignored by Go; on Windows, console control events follow the Go runtime.

Node keeps a few dozen file descriptors open for its event loop, thread pool and V8 platform threads. Under a low `RLIMIT_NOFILE`, TS fails where Go still verifies: Node 22.22.2 on a 4-CPU Linux host needs 35 descriptors for `verify` of a git bundle; with 20 to 34 it fails `spawnSync git` with `EMFILE`, and with fewer it dies at startup (an error, an abort or a crash). The threshold grows with the CPU count and changes between Node versions, so it is not modelled.

## Starting git

`spawnSync` is ported from libuv and the C library Node's official builds use. On Linux the executable lookup is glibc's `execvp` (a candidate that fails with `ENOEXEC`, such as a script without a `#!` line, is run by `/bin/sh`; `ESTALE`, `ENODEV` and `ETIMEDOUT` move on to the next PATH entry; a PATH entry of 4,096 bytes or more is skipped and the bare name is tried in the working directory next; the default search path is `/bin:/usr/bin`); on macOS it is libuv's own search over `posix_spawn`. Child sockets get libuv's 64 KiB buffers, descriptors 0 to 15 and the run above them are close-on-exec from startup (`uv_disable_stdio_inheritance`), environment names that are array indices (and, on Linux, the empty name) are dropped as `{...process.env}` drops them, and an errno libuv has no name for prints as `Unknown system error -N`. On Windows git is created with `CREATE_NO_WINDOW`, in a kill-on-close job object, with 64 KiB pipes, without the hidden `=X:` variables, and with an 8.3 working directory when the cwd is `MAX_PATH` or longer. Remaining differences: when every PATH entry is skipped for length, glibc reports whatever errno was left over in the child (`EINVAL` or `ENOSYS` depending on the host), and Go reports `ENOENT`; Node built on musl (Alpine) has musl's `execvp`, which does not run `ENOEXEC` files through `/bin/sh` and searches `/usr/local/bin:/bin:/usr/bin` by default; on macOS, Go starts git with fork and exec rather than `posix_spawn`, so a malformed Mach-O fails with `exit null` instead of `Unknown system error -85` (EBADEXEC), and libuv aborts Node outright when every PATH entry is too long; Go on Windows passes the environment block unsorted.

## Working directory errors and the C library

`process.cwd()` is libuv's `uv_cwd` over the C library's `getcwd`, and its error codes come from that library. Go ports glibc's `getcwd` on Linux (the `getcwd` syscall, then `__getcwd_generic`'s walk up through `..` when the kernel cannot return the path: longer than a page, or outside the process root after `chroot(2)`) and Apple Libc's on macOS (the `F_GETPATH` fast path checked against `.`, then the same kind of walk, keeping the first `fstatat` error), with `uv_cwd`'s retry that turns a path exactly one byte too long into `ENOBUFS`. `TestLiveCwdErrorsMatchNode` compares `verify` from deleted, recreated, over-long (short and long segments around 4,096 bytes), unreadable and chrooted working directories with Node on Linux. musl (Alpine) has no fallback walk: a cwd longer than a page gives `ENAMETOOLONG` and a cwd outside the root gives `ENOENT` there, where Go, like glibc Node, gives `ENOBUFS`/`ERANGE` and the real path. The macOS port has not been run here (the reviewers' macOS cases were checked against Apple's source). Other Unix systems use Go's `getcwd`.

## `ENOTDIR` on Windows

When a path component that should be a directory is a file (`file.json/x`), Linux reports `ENOTDIR` while Windows (libuv maps `ERROR_PATH_NOT_FOUND` to `ENOENT`) reports `ENOENT`. Go on Windows reports `ENOTDIR` in that case, deliberately: the Linux-generated goldens contain this error (`git-unbound__hashes-enotdir`, `manifest.json/x` declared in `hashes.txt`), and one expected output on every OS keeps the corpus portable. This is a deliberate divergence from TS on Windows, listed in the spec's done criteria. A missing parent directory is `ENOENT` everywhere. All other Win32 errors follow libuv's `uv_translate_sys_error`.

## Windows paths, lstat and deletion

Go follows Node's Windows fs layer rather than Go's `os` package. Every fs call except `mkdtemp` goes through a port of Node's `ToNamespacedPath` (src/path.cc: its C++ `PathResolve`, then a `\\?\` or `\\?\UNC\` prefix), so Win32 path normalization is off as in Node: names ending in a dot or space and reserved device names (`NUL`, `CON.txt`) are ordinary files, and paths longer than `MAX_PATH` work without `LongPathsEnabled`. Error messages print the namespaced path without its prefix, as Node's `StringFromPath` does, which is the resolved absolute path rather than the path as typed. `lstat` and `stat` port libuv 1.51's `fs__stat_impl` (the open flags, the retry without `FILE_FLAG_OPEN_REPARSE_POINT` for reparse points libuv does not read as links, and the parent-directory lookup after `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION`, where any reparse point is a link to lstat), so an AF_UNIX socket or another reparse point that cannot be opened is an lstat error, and an unreadable junction is a symbolic link. `unlink` and `rmdir` port `fs__unlink_rmdir`: POSIX-semantics deletion that ignores the read-only attribute, falling back to a legacy delete only where the filesystem lacks it. None of this has been run on a Windows host; the ports were checked against the libuv and Node sources and by cross-compilation, and `toNamespacedPath` against `path.win32.toNamespacedPath` for absolute paths.

## WSL symlinks on Windows

Go's `Lstat` follows libuv 1.52 (Node 22.23 and later): a WSL symlink (`IO_REPARSE_TAG_LX_SYMLINK`) is a symbolic link. libuv 1.51 (Node 22.22) has no case for that tag and retries with a following stat, which Win32 cannot resolve, so `lstatSync` throws. Either way the verifiers reject the file; only the error line differs.
