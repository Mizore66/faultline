# Known differences between Go `fl` and frozen TS (`faa98c0`)

Every intentional divergence is listed here. Anything not listed is a bug.

## Locale-dependent key order (TS bug, not reproduced)

TS `canonicalJson` sorts object keys with `localeCompare`, which uses the machine's ICU default locale. Under `sv-SE`, Node sorts `å ä ö` after `z`; under `tr-TR`, it orders `I` before `i`. Go always uses the en-US (CLDR root) order that CI and `C.UTF-8` machines produce. Bundles written under an affected locale with affected keys already fail TS verification on en-US machines.

Go's collation (`internal/collation`) is generated from the ICU 78 root collation data (Unicode 17, CLDR 48) that official Node 22 builds ship from 22.22.1 on, and follows ICU's comparison, not a plain UCA key compare: `internal/collation/iter.go` ports ICU's `FCDUTF16CollationIterator` and `CollationIterator` (incremental FCD check, contraction and discontiguous-contraction matching with its look-ahead and backtracking, prefix contexts), so mark runs that ICU leaves un-normalized after contraction look-ahead collate as in ICU; ICU's contraction and prefix data (U+FDD0 rows excluded as genuca does); and `RuleBasedCollator::doCompare`'s identical-prefix skip and early exit at the first primary difference. The identical-prefix skip makes `localeCompare` non-transitive on some inputs, so `SortLocale` runs a port of V8's TimSort. Parity is checked against Node by `TestLiveCollationAllCodePoints` (every code point), `TestLiveCollationRules` (every contraction and prefix key with inserted, reordered and dropped marks and U+FDD0/U+FDD1 sequences), `TestLiveCollationMarkRuns` (contraction starters followed by supplementary and BMP mark runs, each string against its NFD and NFC forms, reorderings and shared prefixes) and `TestLiveSortLocale`.

**Minimum Node version.** Earlier Node 22 releases bundled ICU 74 (22.0), 75.1 (22.1) and 76/77 before ICU 78. Bundles written by those releases whose overlay paths or JSON keys contain characters assigned after their Unicode version (for example U+1FAE9, Unicode 16) may use an order Go rejects (`overlay records are not in canonical path order`, or a different canonical-JSON digest). Current Node 22 TS agrees with Go. A Node built against a system ICU (`--with-intl=system-icu`) can differ the same way.

## Directory listing order on Windows

Node's `readdirSync` returns byte-sorted names on Linux and macOS but filesystem order on Windows (NTFS: case-insensitive upcase order). Go returns byte-sorted names everywhere, so Go on Windows matches TS on Linux. This affects the order of error lines that enumerate files, and, because the file walkers stop at the first symlink, special file or oversized file they meet, which file such an error names when a bundle has two offending entries (for example `analysis.json` before `ROOT.sha256` on NTFS, the reverse in byte order).

## Git's default object format

Not an output difference, but an environment dependency of both implementations. The verifier creates its temporary repository with a plain `git init --bare` (`src/git-proof-bundle.ts:931`), which follows `GIT_DEFAULT_HASH` and `init.defaultObjectFormat`. A SHA-1 bundle therefore verifies only where git defaults to SHA-1, and a SHA-256 bundle only where it defaults to SHA-256; elsewhere both report `Git bundle extraction failed`. Go runs the same git commands and matches TS in both settings. The golden generator and replay pin `GIT_DEFAULT_HASH=sha1`, and the `git-sha256` base runs with `GIT_DEFAULT_HASH=sha256` (`difftest/testdata/base-env.json`).

## V8 limits

When a zod schema rejects a deeply nested value, TS builds the error text with `JSON.stringify(issues, replacer, 2)` (the `ZodError.message` getter). V8 does this recursively, and past its native stack limit it throws `RangeError: Maximum call stack size exceeded`, which the verifier's catch prints as a `failed safely` line. Go models V8's stack use (`internal/jsjson/stack.go`): each non-empty array or object pushes a frame, empty containers and primitives push none, and objects on V8's slow path (array-index keys, or 128 or more members, which JSON.parse builds in dictionary mode) cost more. The model is fitted per platform and per call site (demo, prevention, git, the git lifecycle ledger, and the demo witness artifact, whose messages are read from deeper JS frames). On Node 22.22.2 linux/amd64 (glibc) it reproduces every measured threshold at every site exactly: the demo verifier still prints the zod message for 2,233 nested arrays, 4,166 single-key objects, 2,232 index-keyed objects or 2,906 alternating arrays and objects, and one more level overflows. The witness site gives 2,232 / 4,164 / 2,231 / 2,905. darwin/arm64 and linux/arm64 are fitted to Node 22.22.2 too (the release CI pins), from the stack-live CI job's measurements at all five sites, and `TestLiveStackThresholdsMatchNode` bisects every site and shape against `node dist/cli.js verify` on linux/amd64, linux/arm64 and darwin/arm64 in CI. Values that mix shapes on the way down (alternating index-keyed and named objects; array, named and index-keyed objects in turn; and the like) can overflow one level earlier or later in TS than the model predicts, at every site and on every platform measured: the per-frame costs are fitted to the pure shapes, and the rounding adds up differently on mixed ones. Measured (last depth whose schema message prints, TS vs Go): linux/amd64 ledger 2,905 vs 2,906 and 2,639 vs 2,640; linux/arm64 prevention manifest 2,104 vs 2,103 and 2,549 vs 2,548, demo manifest 1,869 vs 1,868, prevention body 2,185 vs 2,184; darwin/arm64 demo 3,536 vs 3,535 and 3,162 vs 3,161, witness 2,547 vs 2,548, ledger 3,160 vs 3,161, git frozen record 4,102 vs 4,101 and 3,160 vs 3,159, prevention body 4,112 vs 4,111. At such a depth one side prints the schema message and the other `failed safely: Maximum call stack size exceeded`; both are INVALID. Dictionary mode follows V8's JSON.parse: an object literal with 128 or more named entries, duplicate keys included and index keys excluded, is on the slow path. Other builds are not fitted: musl builds (node:alpine) cost differently from glibc on the same architecture (linux/amd64 Node 22.22.2 musl: arrays 2,155, alternating 2,840, index-keyed 2,231; glibc 2,233, 2,906, 2,232; linux/arm64 differs by up to 78 levels), the stack costs drift between Node releases (darwin/arm64 prints 2,610 nested arrays on 22.22.2 and 2,747 on 22.23.2; linux/arm64 1,781 on 22.13.1 and 1,827 on 22.22.2), and Windows and other targets use the Linux model for their architecture. On those, TS can overflow tens to hundreds of levels earlier or later than Go predicts. `--stack-size` also moves V8's limit. `JSON.parse` is iterative on both sides and has no depth limit.

Go also reproduces V8's other size limits: strings longer than 0x1fffffe8 UTF-16 units (`RangeError: Invalid string length`, from `JSON.stringify`, every error message that embeds input, which Go builds with `jsexc.Concat` where TS uses a template literal, and the CLI's error join), Sets and Maps with more than 2^24 entries (`RangeError: Set maximum size exceeded` / `Map maximum size exceeded`, at the Go ports of the TS Sets and Maps, all of which are built before any comparison as in TS), and argument spreads (`errors.push(...list)`, `files.push(...collectFiles(...))`), which throw `Maximum call stack size exceeded` once the list passes V8's stack. The limits were bisected exactly through `node dist/cli.js verify` on Node 22.22.2: the demo walker passes 125,576 files one directory below the bundle root on linux/amd64 (31 fewer per further level), 110,189 on linux/arm64 and 110,181 on darwin/arm64 (32 fewer per level); git semantics errors 125,587 / 110,201 / 110,193; lifecycle-ledger errors 125,562 / 110,175 / 110,167. Node built on musl overflows about 20 elements earlier on linux/arm64, windows/arm64 uses the linux/arm64 values and other targets the linux/amd64 ones without having been measured. Node 22's `rmSync(path, { recursive: true })` is the recursive JS `rimrafSync`, so removing the git verifier's temporary bare repository overflows V8's stack when it holds an entry more than 1,672 levels deep on linux/amd64 or 1,375 on linux/arm64 (Node 22.22.2, glibc and musl; a file and an empty directory count alike), for example from a deep global `init.templateDir` or a hook. Go's rimraf throws the same `Maximum call stack size exceeded` at that depth and leaves the tree behind as TS does; darwin cannot reach the depth (PATH_MAX). The walker's limits were fitted on bundles whose walk is short. Once the walk has run tens of thousands of iterations before the big spread (60,000 files in the root, or 20,000 directories), V8 has tiered `collectFiles` up and Node overflows 6 elements earlier at the same depth (110,175 instead of 110,181 on darwin/arm64, 110,183 instead of 110,189 on linux/arm64), so a directory holding 110,176 to 110,181 files at depth 1 on darwin/arm64 (110,184 to 110,189 on linux/arm64) makes TS fail safely with a stack overflow, where Go walks it; the model does not follow V8's tiering. `TestLiveSpreadLimitsMatchNode` checks the spread limits against Node on linux/amd64, linux/arm64 and darwin/arm64 in CI, and `TestLiveRimrafDepthMatchesNode` the rimraf depth on Linux (it skips on darwin, which cannot reach the depth). Some allocations make V8 abort the process, and Go aborts the same way. JSON.parse arrays of 2^27 or more elements print the V8 fatal-error header with the real length (`# Fatal JavaScript invalid size error 134217729 (see crbug.com/1201626)`) and die by SIGTRAP (exit 133). An object's index-keyed entries (duplicates included) go into a NumberDictionary when that is smaller than a FixedArray up to the largest index (V8's `ShouldConvertToSlowElements`: 9 × the dictionary capacity for the entry count, at most the largest index + 1), otherwise into that FixedArray: a FixedArray of 2^27 or more slots aborts the same way without the crbug note (`{"0":0, …5,592,406 entries…, "134217727":0}`), and a dictionary of 22,369,622 or more entries fails like a NameDictionary of 22,369,622 or more named entries (duplicates included): Node's `FATAL ERROR: invalid table size Allocation failed - JavaScript heap out of memory` report and SIGABRT (exit 134). `String.prototype.split` into 2^27 or more parts aborts like the FixedArray (a demo `hashes.txt` of 134,217,728 lines or more). Go builds the object before it aborts where V8 aborts while sizing it, so under a memory limit that Node's peak fits in (about 2 GB for 22,369,622 named keys) Go can be killed by the OOM killer (exit 137, no output) instead. Node's GC trace, native stack trace and `#FailureMessage Object` address are not reproduced. A utf8 read of a file of 0x1fffffe8 bytes or more fails with `Cannot create a string longer than 0x1fffffe8 characters` in both. Both read to the end of the file without calling fstat (Node's `ReadFileUtf8`), so the size a filesystem reports does not matter; but Node keeps every byte before checking and Go only counts the bytes past the limit, so under a memory limit smaller than the file TS is killed by the OOM killer (exit 137, no stdout) where Go prints the error.

## Stdout write errors

Go builds stdout the way Node's `createWritableStdioStream` does, from a port of libuv's `uv_guess_handle`. A regular file or character device is a `SyncWriteStream`: one `write(2)` per chunk, a short count ignored (a full disk or `RLIMIT_FSIZE` reached in the middle of a chunk truncates the output silently), and a failing call reported as `Error: <CODE>: <description>, write` (`/dev/full` gives `Error: ENOSPC: no space left on device, write`). A pipe, stream socket or terminal is a libuv stream: everything is written, waiting while the descriptor would block (for example after another process set `O_NONBLOCK` on a shared pipe), and a failure is `Error: write <CODE>`. UDP sockets and handles libuv cannot classify (a datagram Unix socket, a directory) get Node's dummy writer, which discards the output. As in Node, stdout is classified on first use (the first write, after the checks), so a terminal that hangs up during verification gets the file form, and a terminal, pipe or FIFO that fd 1 has open read-only is a stream libuv cannot write to, which fails with `Error: write EPIPE` without a write. Both runtimes ignore SIGPIPE, so a pipe whose reader has gone is `Error: write EPIPE`, and any stdout write error exits 1. On Windows, Node writes pipes synchronously, so a pipe error has the file form, `ERROR_BROKEN_PIPE` and `ERROR_NO_DATA` are `EPIPE`, and a handle not opened for writing is `EBADF` (`fs__write` turns `ERROR_ACCESS_DENIED` into `ERROR_INVALID_FLAGS`), as in libuv. On a stream, `ENOBUFS` waits like `EAGAIN`, and on macOS `EPROTOTYPE` is `ECONNRESET`, as in `uv__try_write`. Error codes come from libuv's full `uv_err_name` table; an errno it cannot name is `Unknown system error -N` in both forms, as in every error Node throws from C++ (the fs calls and `uv_cwd` included). Node reports the error as an unhandled `'error'` event, a stack trace around the error line; Go prints the error line only. `TestLiveStdoutMatchesNode` compares these cases with Node on Linux. The CLI's own error output goes through `process.stderr`, which Node creates while its modules load, so fd 2 is classified at startup and gets the dummy writer for UDP and unclassified sockets too (`FaultLine error:` lines reach a TCP or stream socket but not a datagram or `SOCK_SEQPACKET` one); V8's fatal reports and the stdout error line are printed with C stdio and reach fd 2 whatever it is, in both (`TestLiveStderrMatchesNode`, Linux and macOS). On a Windows console Node decodes the output to UTF-16, writes an LF not preceded by CR as CR LF, and calls `WriteConsoleW` (libuv's `uv__tty_write_bufs`), and Go does the same; its errors are libuv's stream errors (`Error: write EPERM` for a handle not opened for writing). This was checked against libuv's source, not on a Windows console. One oracle pathology is not reproduced: when stdout or stderr is a pseudo-terminal whose master has already closed, Node blocks forever in `uv_tty_init` reopening the terminal (for stderr on every command, even a VALID verify that writes nothing there); Go reports `Error: write EIO` and exits 1 for stdout, and runs normally for stderr.

## Signals and resource limits

Node resets signals 1 to 31 to their default action at startup, ignoring only SIGPIPE and SIGXFSZ, clears the signal mask, and raises its soft `RLIMIT_NOFILE` to the hard limit; libuv resets every signal and the mask in the processes it starts, which inherit the raised limit. Go emulates this from the first package initialized (`internal/boot`). On Linux the signals whose default action ends the process (HUP, INT, QUIT, ABRT, USR2, ALRM, TERM, STKFLT, XCPU, VTALRM, IO, PWR, SYS and the real-time signals from 35) are set to SIG_DFL in the kernel; externally sent SEGV, BUS, FPE, ILL and TRAP are caught and end `fl` by their default action (the Go runtime keeps its handler so that faults in Go code still panic); inherited SIG_IGN on TSTP, TTIN, TTOU and CONT is reset; and then an inherited signal mask is cleared by re-executing `/proc/self/exe` once with an empty mask, before the standard descriptors are marked close-on-exec, so the output reaches the same descriptors. Node clears the mask before it resets any disposition, so a signal left pending under the inherited mask meets the disposition the parent left: the default action, or nothing if it was ignored. Go does the same for the stop signals, whose inherited SIG_IGN is reset only after the mask is cleared, and for a pending SIGPIPE or SIGXFSZ, which ends `fl` before the runtime's signal thread can catch it. The other signals' inherited dispositions are replaced by the Go runtime before any package runs, so `fl` treats them as SIG_DFL: one that the parent both ignored and left pending ends `fl` (for example SIGUSR2, exit 140), where Node discards it. Deaths go through `rt_sigaction`, `rt_sigprocmask` and `tgkill` on the dying thread, with core dumps where the kernel makes them. The soft `RLIMIT_NOFILE` is raised as Node raises it and git inherits it: to the hard limit, or, when the hard limit is `RLIM_INFINITY` (2^63 − 1 on macOS, where it is the default), to the highest value below 2^20 that `setrlimit` accepts (1,048,575 on macOS 26). `TestLiveNofileMatchesNode` compares git's limits with Node on Linux and macOS. `TestLiveSignalsMatchNode` compares the death, the output, and git's signal mask, ignored set and descriptor limit with Node on Linux, including a blocked mask, a signal pending under it (also raised before exec under SIG_DFL or SIG_IGN), and a low soft limit.

On macOS the same signals are caught through os/signal and `fl` dies by re-executing `/bin/sh -c 'kill -N $$'`, since the syscall package exports no `sigaction` or `sigprocmask` there; every other signal is set to SIG_IGN first, so one that arrives while the shell starts cannot replace the first (Node dies of the first). Go learns of a signal on a goroutine, a few milliseconds after Node would have died. `fl` therefore writes nothing and does not exit once a signal has reached it, and when a child dies of a signal `fl` did not send (Ctrl-C, a terminal hang-up or `killpg` reach `fl` and git together) it waits up to 2 s for its own copy before it reports git's death; `TestLiveGroupSignalMatchesNode` checks both on Linux and macOS. A signal sent to `fl` alone at the very end of a run can still let the report out first. A mask or SIG_IGN on the stop signals inherited from the parent stays in effect on macOS, and a `/bin/sh` that ignores SIGQUIT (bash) exits 131 instead. macOS delivers SIGBUS, SIGILL and SIGSEGV sent with `kill` with a fault code rather than the code of a user-sent signal, so the Go runtime takes them for a crash in `fl` and exits 2 with a goroutine dump where Node dies by the signal (SIGEMT, SIGFPE and SIGTRAP die correctly). When the parent left SIGBUS or SIGSEGV ignored, the runtime forwards such a signal to that SIG_IGN instead: `fl` carries on and can print `VALID` and exit 0, where Node, which resets them to SIG_DFL, dies by the signal. Linux is not affected.

Remaining differences on every Unix system: a signal that arrives before the Go runtime has initialized any package (under a millisecond on an idle machine, over 10 ms on a heavily loaded one, and again while the image that clears an inherited mask on Linux starts) is handled by the runtime (ALRM, USR2 and the like are dropped, QUIT and ABRT dump goroutines); SIGPROF is consumed by the Go runtime, so it doesn't stop `fl`; SIGUSR1 starts Node's inspector (a "Debugger listening" line on stderr) and is ignored by Go. On musl, Node leaves signal 33 (musl's SIGCANCEL, installed only when a thread is cancelled) at its inherited disposition, so it dies of a `kill -33` and passes an inherited SIG_IGN on to git; glibc installs its own handler there (SIGSETXID), as the Go runtime does, and `fl` follows glibc, which a static binary cannot tell from musl. On Linux, a real-time signal (35 to 64) inherited as SIG_IGN stays ignored in Node and in its git, while `fl` sets it to SIG_DFL: the Go runtime has replaced the inherited disposition with its own handler before any package initializes and keeps the original out of reach. If the re-execution fails (a binary on a `noexec` mount), `fl` continues with the inherited mask, and git inherits it too. On Windows, console control events follow the Go runtime.

Node keeps a few dozen file descriptors open for its event loop, thread pool, V8 platform threads and module loading. With a hard `RLIMIT_NOFILE` of about 30 or less, TS fails where Go still verifies (from 15; below that Go prints `spawnSync git EMFILE`). Measured with Node 22.22.2 on Linux, on 1 to 6 CPUs alike, when the parent passes only descriptors 0 to 2: 30 verifies; 18 to 29 print `spawnSync git EMFILE`; 17 fails to load one of Node's own modules with `EMFILE`; about 13 to 16 die by SIGSEGV with no output (exit 139); lower limits abort in `uv_loop_init` (exit 134). Each further descriptor the parent leaves open raises the upper thresholds by one (31 is then the first that verifies). The numbers change between Node versions, so they are not modelled.

## Starting git

`spawnSync` is ported from libuv and the C library Node's official builds use. On Linux the executable lookup is glibc's `execvp` (a candidate that fails with `ENOEXEC`, such as a script without a `#!` line, is run by `/bin/sh`; `ESTALE`, `ENODEV` and `ETIMEDOUT` move on to the next PATH entry; a PATH entry of 4,096 bytes or more is skipped and the bare name is tried in the working directory next; the default search path is `/bin:/usr/bin`); on macOS it is libuv's own search over `posix_spawn`. Child sockets get libuv's 64 KiB buffers, descriptors 0 to 15 and the run above them are close-on-exec from startup (`uv_disable_stdio_inheritance`), environment names that are array indices (and, on Linux, the empty name) are dropped as `{...process.env}` drops them, and an errno libuv has no name for prints as `Unknown system error -N`. On Windows git is created with `CREATE_NO_WINDOW`, in a kill-on-close job object, with 64 KiB pipes, without the hidden `=X:` variables, and with an 8.3 working directory when the cwd is 259 UTF-16 units or longer (libuv counts the terminating NUL against `MAX_PATH`, and searches for git from the short form); environment names that differ only in case are reduced to the first in sorted order, as `normalizeSpawnArguments` does on Windows. Remaining differences: when every PATH entry is skipped for length, glibc reports whatever errno was left over in the child (`EINVAL` or `ENOSYS` depending on the host), and Go reports `ENOENT`; Node built on musl (Alpine) has musl's `execvp`, which does not run `ENOEXEC` files through `/bin/sh`, searches `/usr/local/bin:/bin:/usr/bin` by default, skips a PATH entry of 4,096 bytes or more without trying the bare name in the working directory (so a `git` there runs under Go and not under TS), and ends the search on `ESTALE`, `ENODEV` or `ETIMEDOUT` where glibc moves on; a static binary cannot tell which C library the host's Node uses, so Go follows glibc; on macOS, Go starts git with fork and exec rather than `posix_spawn`, so a malformed Mach-O fails with `exit null` instead of `Unknown system error -85` (EBADEXEC), and libuv aborts Node outright when every PATH entry is too long; on Windows, Go sorts and deduplicates the names as `normalizeSpawnArguments` does and looks each kept name up again with `GetEnvironmentVariableW`, as Node's `process.env` does (so `Path=A` before `PATH=B` gives git `PATH=A`, and a lone surrogate in a value becomes three U+FFFD), but uppercases names with Go's simple case mapping where Node's `toUpperCase` maps a few letters to several (ß to SS); libuv lets git inherit every inheritable handle of the Node process, and Go only the three standard ones.

## Working directory errors and the C library

`process.cwd()` is libuv's `uv_cwd` over the C library's `getcwd`, and its error codes come from that library. Go ports glibc's `getcwd` on Linux (the `getcwd` syscall, then `__getcwd_generic`'s walk up through `..` when the kernel cannot return the path: longer than a page, or outside the process root after `chroot(2)`) and Apple Libc's on macOS (the `F_GETPATH` fast path checked against `.`, then the same kind of walk, keeping the first `fstatat` error), with `uv_cwd`'s retry that turns a path exactly one byte too long into `ENOBUFS`. `TestLiveCwdErrorsMatchNode` compares `verify` from deleted, recreated, over-long (short and long segments around 4,096 bytes), unreadable and chrooted working directories with Node on Linux. musl (Alpine) has no fallback walk: a cwd longer than a page gives `ENAMETOOLONG` and a cwd outside the root gives `ENOENT` there, where Go, like glibc Node, gives `ENOBUFS`/`ERANGE` and the real path. The macOS port has not been run here (the reviewers' macOS cases were checked against Apple's source). Other Unix systems use Go's `getcwd`.

## Directory listings on Linux

Node's `readdirSync` is libuv's `scandir`, which reads entries through the C library's `readdir`. glibc 2.28 to 2.36 (Debian 11 and 12, RHEL 8 and 9, Ubuntu 22.04) skips entries whose inode number is 0, which some FUSE filesystems and old XFS report for live files; glibc 2.37 and later and musl list them. One static binary cannot follow both, so Go follows glibc 2.36, the C library most LTS systems run Node on, in the bundle walkers, rimraf and the `getcwd` walk: on glibc 2.37+ or musl hosts with such a filesystem, Node sees files Go does not. Entries whose type libuv cannot name (`DT_UNKNOWN` from XFS without `ftype`, some NFS and FUSE, or any `d_type` other than FIFO, CHR, DIR, BLK, REG, LNK and SOCK) are `lstat`ed by Node inside `readdirSync({ withFileTypes: true })`, in order, and Go does the same on Linux, so a failing `lstat` is reported before the walker looks at earlier entries; on other Unix systems Go does not read `d_type` and such a failure is reported when the walker reaches the entry. Directories are opened with `O_DIRECTORY` and then `fstat`ed, as glibc's `opendir` does. The `d_ino` 0 skip and the `d_type` rule were checked on FUSE (glibc 2.36 and 2.39). glibc 2.28 to 2.32 also skip, inside the `getcwd` walk only, entries whose `d_type` is neither `DT_DIR` nor `DT_UNKNOWN`; Go follows 2.33 to 2.36 there, so on Debian 11, RHEL 8 or Ubuntu 20.04 a directory in the cwd's path reported with a wrong type can make Node fail with `ENOENT` where Go finds the path. `existsSync` is `access(2)` with `F_OK` and Go's port calls `access` too, so a filesystem that answers `access` and `stat` differently gives the same answer in both. `os.tmpdir()` reads `TMPDIR`, `TMP` and `TEMP` through `SafeGetenv`, which ignores them in setuid, setgid and (on Linux) `AT_SECURE` processes unless the only permitted capability is `CAP_NET_BIND_SERVICE`; Go applies the same test (`TestLiveTmpdirSetidMatchesNode`).

## `ENOTDIR` on Windows

When a path component that should be a directory is a file (`file.json/x`), Linux reports `ENOTDIR` while Windows (libuv maps `ERROR_PATH_NOT_FOUND` to `ENOENT`) reports `ENOENT`. Go on Windows reports `ENOTDIR` in that case, deliberately: the Linux-generated goldens contain this error (`git-unbound__hashes-enotdir`, `manifest.json/x` declared in `hashes.txt`), and one expected output on every OS keeps the corpus portable. This is a deliberate divergence from TS on Windows, listed in the spec's done criteria. A missing parent directory is `ENOENT` everywhere. Listing a file (`scandir`) is `ENOTDIR` in both, because libuv's `fs__scandir` sets that code itself. All other Win32 errors follow libuv's `uv_translate_sys_error`.

## Windows paths, lstat and deletion

Go follows Node's Windows fs layer rather than Go's `os` package. Every fs call except `mkdtemp` goes through a port of Node's `ToNamespacedPath` (src/path.cc: its C++ `PathResolve`, then a `\\?\` or `\\?\UNC\` prefix), so Win32 path normalization is off as in Node: names ending in a dot or space and reserved device names (`NUL`, `CON.txt`) are ordinary files, and paths longer than `MAX_PATH` work without `LongPathsEnabled`. Error messages print the namespaced path without its prefix, as Node's `StringFromPath` does, which is the resolved absolute path rather than the path as typed. `lstat` and `stat` port libuv 1.51's `fs__stat_impl` (the open flags, the retry without `FILE_FLAG_OPEN_REPARSE_POINT` for reparse points libuv does not read as links, and the parent-directory lookup after `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION`, where any reparse point is a link to lstat), so an AF_UNIX socket or another reparse point that cannot be opened is an lstat error, and an unreadable junction is a symbolic link. `unlink` and `rmdir` port `fs__unlink_rmdir`: POSIX-semantics deletion that ignores the read-only attribute, falling back to a legacy delete only where the filesystem lacks it. None of this has been run on a Windows host; the ports were checked against the libuv and Node sources and by cross-compilation, and `toNamespacedPath` against `path.win32.toNamespacedPath` for absolute paths.

The TS bundle walkers recurse on V8's stack, so a bundle nested thousands of directories deep fails with `failed safely: Maximum call stack size exceeded`. On Linux and macOS `PATH_MAX` stops such a tree first, but Windows paths are namespaced (`\\?\`, 32,767 units), and Go's walkers have no depth limit: a bundle of a few thousand nested empty directories (about 3,700 for git, 3,900 for demo and 4,800 for prevention bundles, extrapolated from linux/arm64) is INVALID in TS and VALID in Go there. The per-level cost has not been measured on Windows, so it is not modelled.

## WSL symlinks on Windows

Go's `Lstat` follows libuv 1.52 (Node 22.23 and later): a WSL symlink (`IO_REPARSE_TAG_LX_SYMLINK`) is a symbolic link. libuv 1.51 (Node 22.22) has no case for that tag and retries with a following stat, which Win32 cannot resolve, so `lstatSync` throws. Either way the verifiers reject the file; only the error line differs.

## Memory use

Go holds a JSON input as UTF-16 while parsing it and builds one `Obj` per object, so on large JSON inputs it needs 4 to 6 times Node's memory (a 40 MB document of 5M small objects peaks at about 1.9 GB in Go against 0.5 GB in Node). Under a memory limit this can decide the outcome: in a 4 GB container a demo bundle whose `analysis.json` holds an 80 MB array is verified by TS (INVALID, with the full error list) and gets Go killed by the OOM killer (exit 137, no output). The demo verifier reads `analysis.json` without a size cap, as TS does; the git verifier's per-artifact cap of 128 MiB is too high to prevent it. Outputs are identical whenever both finish. Collation builds sort keys lazily, as far as comparisons need them, and skips the identical prefix of two keys as ICU does, so long record keys cost about what they cost Node whether they differ early or late (2,000 keys sharing a 3,000-character U+FDFA prefix: 0.8 s and 298 MB in Go, 0.5 s and 282 MB in TS).

## Oracle pathologies not reproduced

- ICU 78's discontiguous-contraction back-off can loop forever: a TRAILING_CCC contraction starter, an out-of-order run with a supplementary mark, U+0344 and a starter (`ا\u{11100}\u{16AF2}\u{0344}ꪫ` against the same string without the last code point) make ICU's iterator step back past the starter and re-read it. Go ports the iterator and hangs the same way on the same pairs. Once memory runs out, ICU's CE buffer allocation fails and `localeCompare` returns an arbitrary sign, while Go dies of out-of-memory (exit 2).
- Loading `dist/cli.js` instantiates undici's WebAssembly HTTP parser, which reserves about 10 GiB of address space: under `ulimit -v` of 10 GiB or less, TS prints the verdict and then exits 1 with `RangeError: WebAssembly.instantiate(): Out of memory`, where Go exits with the verdict's status.
- On macOS, Node links CoreFoundation, which sets `__CF_USER_TEXT_ENCODING=0x<uid>:0x0:0x0` in Node's environment when it is missing, invalid or belongs to another uid, so git sees that variable under TS only. Git's output does not depend on it.
